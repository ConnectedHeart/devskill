# 서버 간 호출 401 원인 좁히기와 로그 설계

> 분류: 인증·보안 · 최근 갱신: 2026-10-22

## 한 줄 요약
두 서버가 서로를 부르는 인증 흐름에서 401이 나면, 응답 시간과 "상대가 되물어 왔는가"로 어느 쪽이 거부했는지 먼저 가르고, 평소 로그에는 비밀 값 대신 유무·길이와 추적 번호를 남겨 둔다.

## 내용
- **구조**: A가 B를 부르면서 자격증명을 넘기고, B가 그 자격증명이 진짜인지 A의 API를 되불러 확인하는 형태가 흔하다. 이때 401은 세 곳에서 날 수 있다. B가 값의 형식만 보고 자체 거부, B가 되물었는데 A가 거부, B의 권한 판정 단계에서 거부.
- **가르는 기준**
  - A의 접근 로그에 그 시각 B의 되묻는 호출이 없다 → B가 받은 값만 보고 거부한 것. 응답이 수 ms로 매우 빠른 것도 같은 신호다.
  - 되묻는 호출이 있고 그 응답이 401이다 → A의 검증이 실패한 것. 검증 중 DB 조회 로그 없이 0~2ms 만에 끝났다면 형식 검사에서 떨어진 것이다.
  - 200인데 기능이 막혔다 → 인증이 아니라 권한 설정이다. "인증 거부"와 "허용 안 함"을 로그 문구로 구분해 두면 바로 갈린다.
- **캐시가 있으면 로그가 안 남는다**: 판정 결과를 캐시하는 구조에서는 캐시 적중 시 상대를 부르지 않아 로그가 없다. 원인을 잡으려면 캐시가 비워지는 동작(재로그인 등) 직후의 로그를 봐야 한다.
- **"없음"과 "형식 오류"를 구분해 남기기**: 자격증명의 길이를 로그에 남길 때 "찾지 못함"(예: `length=-1`)과 "찾았는데 형식이 틀림"(실제 길이)을 다른 값으로 남기면 상대가 약속과 다른 위치(다른 헤더, 본문)로 보내는 경우를 바로 알 수 있다.
- **401과 403을 먼저 구분한다**: 401(Unauthorized)은 "누구인지 확인하지 못함"(토큰·세션이 없거나 만료·형식 오류), 403(Forbidden)은 "누구인지는 알지만 이 기능 권한이 없음"이다. 토큰 없이 401, 일반 사용자 토큰으로 403이 나오면 API는 설계대로 동작하는 것이고, 문제는 호출자가 보낸 자격증명 쪽이다. 401이 1ms 만에 나고 컨트롤러 진입 로그가 없으면 인증 인터셉터 단계에서 떨어진 것이다.
- **요청 헤더 "이름 목록"을 남기면 위치 불일치가 바로 보인다**: 값은 빼고 헤더 이름만(`[host, x-custom-token, traceparent]`처럼) 남기면, 호출자가 `Authorization: Bearer` 대신 자체 정의 헤더에 토큰을 실어 보내 서버가 "토큰 없음"으로 판정한 경우를 한 줄로 확인할 수 있다. 같은 서버를 부르는 다른 클라이언트는 정상이고 특정 클라이언트만 401이면 이 경우를 먼저 의심한다.
- **WAS access 로그에 요청이 아예 없을 때**: 톰캣 같은 WAS는 도착한 요청을 404든 401이든 access 로그에 한 줄씩 남긴다. 상대는 401을 받았다는데 access 로그에 없으면 그 요청은 WAS까지 오지 않은 것이다. 흔한 이유는 상대에 설정된 주소(스킴·호스트·포트)가 다름, 앞단 L4·프록시가 다른 서버로 넘김, TLS 연결 단계 실패(인증서 신뢰·호스트 이름 검사, 이때 상대에는 401이 아니라 연결 오류가 남음), 중간 게이트웨이나 상대 서버 자신이 401을 줌이다.
  - 애플리케이션 로그와 함께 보면 가를 수 있다. 애플리케이션 로그에는 있는데 access 로그에 없으면 access 로그 쪽 문제다. 톰캣 access 로그는 기본으로 버퍼에 모았다가 몇 초마다 쓰고, `<Host>`마다 다른 파일에 남으므로 IP나 다른 호스트 이름으로 부르면 다른 파일에 있을 수 있다.
  - 우리 서버가 401에 항상 붙이는 응답 헤더(추적 번호)와 정해진 오류 본문 형식이 있으면, 상대가 받은 401에 그것이 없을 때 "우리가 준 401이 아니다"라고 바로 말할 수 있다.
- **같은 흐름의 다음 호출을 본다**: 1회용 코드로 세션을 등록하는 호출이 200이고 그 직후 다음 API가 401이라면, 등록은 성공했고 다음 호출에서 자격증명을 다른 헤더에 실었는지 먼저 본다. 추적 번호가 같은 줄을 시간순으로 놓으면 흐름이 한눈에 보인다.
- **가설은 로그로 확인하고 버린다**: "세션 만료 후 재등록이 기존 행을 재사용해 살아나지 않는다" 같은 코드상 그럴듯한 가설도, 거부 지점마다 사유(토큰 없음/해석 실패/세션 행 없음/만료/테넌트 불일치)를 남기는 진단 로그로 재현해 보면 실제 원인이 전혀 다를 수 있다. 진단 로그는 판정 분기마다 사유 문자열을 남기도록 넣는 것이 효과적이다.
- **추적 번호(trace id)**: 요청마다 번호를 붙여 시작·종료 로그, 응답 헤더, 오류 본문에 같은 값을 넣는다. 호출자가 W3C `traceparent` 헤더를 보내면 그 번호를 이어받고 없으면 새로 만든다. 상대 팀과 "몇 시쯤 요청"이 아니라 번호로 같은 요청을 지목할 수 있다.
- **비밀 값은 로그에 남기지 않는다**: 토큰, 세션 값, 1회용 코드는 값 대신 유무와 길이만 남긴다. 값이 로그에 있으면 로그를 볼 수 있는 사람이 그 사용자로 API를 부를 수 있다. 추적이 꼭 필요하면 앞 몇 글자만 남긴다.
- **1회용 코드 교환에서의 판단**: 코드 교환 호출이 200이면 코드 자체는 유효했다는 뜻이다. 코드가 틀렸거나 만료·재사용이면 교환 단계에서 4xx가 난다. 그러므로 200 이후의 실패는 응답 내용(자격증명이 실린 위치와 형식)의 문제다.
- **GUID와 UUID**: 같은 128비트 값의 두 이름이다(GUID는 Microsoft 계열 명칭). 표기는 환경마다 다를 수 있다. 하이픈 포함 36자가 기본이고, 하이픈 없는 32자나 중괄호를 붙인 38자도 쓰인다. 형식을 엄격히 검사하는 쪽과 연동할 때는 표기를 맞춘다. 세 번째 구간의 첫 글자가 `4`면 버전 4(무작위) 값이다.
- **난독화는 인증이 아니다**: 정해진 규칙으로 글자를 바꾸는 방식은 규칙을 아는 누구나 만들 수 있다. 그런 값을 받을 때는 풀어서 나온 내용(발급자 표시, 세션 식별자 형식)을 검사하고, 최종 판단은 그 식별자가 서버에 살아 있는 세션인지로 한다.
- **세션 ID를 API 자격증명으로 쓰면**: 그 값을 아는 쪽은 API 범위에 그치지 않고 화면 로그인까지 할 수 있는 경우가 많다. 범위를 묶으려면 세션 종류를 구분하거나 API 전용 값을 따로 발급한다.

## 예시
```
# 상대가 값만 보고 거부한 경우 (되묻는 호출 없음, 4ms)
12:00:01.604  외부 호출 응답 url=https://b.example.com/check status=401 bodyLength=0

# 상대가 되물었고 우리 쪽이 거부한 경우
12:00:01.331  요청 시작: GET /api/me caller=- traceId=…
12:00:01.333  요청 종료: GET /api/me status=401 elapsedMs=2
12:00:01.378  외부 호출 응답 url=https://b.example.com/check status=401
```

## 주의할 점
- 원인 확인용으로 응답 헤더·본문 전체를 남기는 임시 로그를 넣었다면, 눈에 띄는 접두어와 "확인 후 제거" 주석을 달고 커밋 전에 반드시 지운다. 저장해 둔 로그 파일에도 같은 값이 남는다.
- 테스트용으로 세션 ID 전체나 요청 본문 전문을 남기는 빌드를 테스트 서버에 올렸다면, 확인이 끝난 뒤 소스를 되돌리는 것만으로는 부족하다. 서버에 떠 있는 빌드도 다시 배포해야 그 값이 더 이상 쌓이지 않는다.
- 확인 스크립트가 "계정 환경변수가 없으면 로그인 단계를 건너뛴다"로 짜여 있어도, 그 변수가 OS 사용자 환경변수로 등록돼 있으면 자식 프로세스에 자동으로 들어가 의도치 않게 로그인한다. 원격 서버용 스크립트는 실행할 때만 넣는 전용 변수를 읽게 한다.
- 디버그 로그가 많은 서버에서는 몇 분만 지나도 해당 구간이 밀려난다. 재현 직후 바로 로그를 떠 둔다.
- 문서마다 헤더 이름이 다르게 적혀 있으면 작성 시점이 다른 것이다. 명세(OpenAPI)에 응답 헤더 정의가 없을 수도 있으니 실제 응답으로 확인한다.
