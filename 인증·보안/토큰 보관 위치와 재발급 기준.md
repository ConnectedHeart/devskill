# 토큰 보관 위치와 재발급 기준

> 분류: 인증·보안 · 최근 갱신: 2026-10-06

## 한 줄 요약
서버가 있는 웹 애플리케이션에서 access token·refresh token을 어디에 둘지와, "필요할 때만 재발급"을 구현할 때 정해야 하는 기준을 정리한다.

## 내용
**보관 위치 비교**

| 위치 | 장점 | 단점 |
|---|---|---|
| 서버 메모리 캐시 | 요청 크기가 늘지 않음, 구현 쉬움 | 서버마다 따로 보관, 재시작하면 사라짐 |
| HttpOnly 쿠키 | 서버가 상태를 갖지 않아 여러 대여도 동작, 로그아웃 때 쿠키 삭제로 정리 | 토큰(1~2KB)이 모든 요청에 실림, 쿠키 하나 약 4KB 한도, 요청 헤더 전체 한도(톰캣 기본 8KB) |
| 서버 세션 | 가장 단순, 세션 무효화로 정리 | 세션 만료·서버 이동 시 사라짐 |
| DB | 서버 간 완전 공유, 로그아웃이 즉시 전체 반영 | 요청마다 키 조회 1회, 암호화 저장 필요 |

- refresh token은 새 access token을 계속 만들어 낼 수 있는 장기 자격증명이다. 서버가 있는 애플리케이션은 이것을 서버에만 두고 브라우저에는 의미 없는 무작위 세션 식별자만 주는 구조가 권고된다. 이렇게 하면 쿠키가 탈취돼도 공격자는 애플리케이션을 거쳐야만 토큰을 얻고, 행 삭제로 즉시 끊을 수 있다.
- refresh token을 메모리 캐시나 서버 세션에만 두면, 재시작하거나 다른 서버로 요청이 갔을 때 값이 사라진다. 다시 받으려면 사용자 재인증이 필요하므로 이 용도에는 맞지 않는다.
- 키로 한 행을 찾는 DB 조회는 보통 1ms 안쪽이라, 요청마다 인증 서버에 HTTP로 다녀오는 것보다 가볍다. 필요하면 DB 앞에 짧은 메모리 캐시(access token만, 수십 초)를 둘 수 있지만, 다중 서버에서는 로그아웃 후에도 다른 서버 캐시에 그 시간만큼 남는다.

**재발급 기준**
- 보관된 access token의 남은 수명은 JWT 가운데 부분(payload)을 Base64URL 디코딩해 `exp`를 읽으면 알 수 있다. 재발급 여부 판단용이라면 여기서 서명 검증은 필요 없다(검증은 토큰을 받는 쪽이 한다).
- access token과 refresh token 수명이 같으면 "만료됐을 때 재발급"은 위험하다. 그 시점에 refresh token도 함께 만료돼 재로그인 전까지 기능이 끊긴다. "수명의 절반이 지나면 재발급"처럼 여유를 둔다.
- 화면 쪽에 "만료 N초 전 자동 갱신" 타이머가 있으면 서버의 재사용 기준은 N초보다 넉넉해야 한다. 그렇지 않으면 곧 만료될 같은 토큰을 다시 돌려준다.
- 여러 창이 같은 토큰을 공유하면 갱신 타이머가 같은 순간에 울린다. 몇 초의 무작위 지연을 주면 먼저 간 요청이 갱신하고 나머지는 새 값을 그대로 받는다.
- access token 수명이 짧으면(예: 5분) 재사용 구간도 짧아져 이득이 줄어든다.

**토큰을 페이지에 내려줘야 할 때 (브라우저가 외부 API를 직접 호출하는 구조)**
- 토큰이 들어 있는 응답은 캐시 금지: `Cache-Control: no-store`. 캐시에 남으면 로그아웃 후에도 뒤로 가기나 캐시 파일에서 꺼낼 수 있다.
- URL 쿼리스트링, 서버 로그, 에러 메시지에 싣지 않는다. URL은 방문 기록·접근 로그·Referer에 남는다.
- 스크립트에 넣을 때는 JSON 직렬화 함수를 거친다. `token: "값"`처럼 문자열을 직접 이어 붙이면 값에 `"`나 `</script>`가 있을 때 스크립트 주입이 된다.

**쿠키 공유 범위**
- 쿠키는 창·탭이 아니라 브라우저 프로필과 도메인 단위로 저장된다. 같은 브라우저의 새 창·탭·팝업은 같은 쿠키를 보고, 한 창의 응답이 쿠키를 바꾸면 다른 창의 다음 요청에도 새 값이 실린다.
- 시크릿 창, 다른 브라우저, 다른 프로필은 공유하지 않는다. 포트만 다른 주소는 쿠키가 공유된다(쿠키는 포트를 구분하지 않음).

## 예시
Spring MVC에서 JSON으로 토큰을 돌려주는 메서드는 인터셉터의 `postHandle()`에 기대지 말고 메서드 안에서 헤더를 직접 넣는다. `@ResponseBody`/`ResponseEntity` 응답은 본문이 먼저 기록(커밋)된 뒤 `postHandle()`이 실행돼 그때 넣는 헤더가 반영되지 않을 수 있다.

```java
@RequestMapping("/token")
public ResponseEntity<Map<String, String>> token(HttpServletResponse resp) {
    resp.setHeader("Cache-Control", "no-store");
    resp.setHeader("Pragma", "no-cache");
    // ... 성공·실패 응답 모두에 적용됨
}
```

## 주의할 점
- 쿠키에서 읽은 토큰은 사용자가 바꿀 수 있는 값이다. 재사용 전에 JWT 형식인지, `exp`가 남았는지, 토큰의 사용자가 로그인 사용자와 같은지 확인하고 어긋나면 버린다.
- `Secure` 속성 없이 http로 운영하면 쿠키의 토큰이 모든 요청에 평문으로 실린다.
- "이미 더 민감한 값이 쿠키에 있으니 괜찮다"는 근거가 되지 않는다. 각 값의 보관 방식은 따로 평가한다.
