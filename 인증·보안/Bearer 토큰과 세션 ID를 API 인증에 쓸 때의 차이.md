# Bearer 토큰과 세션 ID를 API 인증에 쓸 때의 차이

> 분류: 인증·보안 · 최근 갱신: 2026-10-07

## 한 줄 요약
`Authorization: Bearer`는 "이 값을 가진 쪽을 주인으로 인정한다"는 방식이라 무엇을 실어 보내느냐가 중요하며, 웹 로그인 세션 ID를 그대로 다른 서버에 넘기면 유출 시 피해 범위가 수명이 짧은 access token보다 훨씬 넓다.

## 내용
- **헤더 구성**: `Authorization`은 인증 정보를 담는 HTTP 표준 헤더, `Bearer`는 인증 방식 이름(소지자, RFC 6750), 그 뒤가 토큰이다.
- **쿠키와의 차이**: 쿠키는 브라우저가 자동으로 붙이고, `Authorization` 헤더는 호출하는 프로그램이 코드로 직접 붙인다. 서버끼리의 API 호출은 브라우저가 아니라서 쿠키가 자동으로 실리지 않는다.
- **OAuth 오류 코드 `invalid_grant`**(RFC 6749): 토큰을 요청하며 낸 증빙이 유효하지 않다는 뜻. 로그인(password grant)에서는 아이디·비밀번호가 틀린 것, 재발급에서는 refresh token을 더 쓸 수 없는 것(만료, 이미 써서 폐기됨, 세션 로그아웃, 사용자 비활성화)이다.
  - 재발급의 `invalid_grant`는 다시 시도해도 계속 실패하므로 저장해 둔 토큰을 지우고 재로그인을 유도한다.
  - `invalid_client`(클라이언트 ID·secret 설정 오류), 통신 오류, 타임아웃은 토큰 자체의 문제가 아니므로 지우지 않고 다음에 다시 시도한다.
  - 같은 401이라도 응답 본문의 `error` 값으로 "사용자 자격 문제"와 "클라이언트 설정 문제"를 구분한다. 존재하지 않는 계정으로 일부러 요청해 `invalid_grant`가 오면 클라이언트 설정은 맞다는 확인이 된다.
- **세션 ID를 토큰 자리에 넘길 때의 위험**
  - 세션 ID는 그 자체가 로그인 증명이다. 알아낸 사람이 자기 브라우저 쿠키에 넣으면 비밀번호 없이 그 사용자가 된다. 암호화되지 않은 값이라는 점은 상관없다(해독할 필요 없이 그대로 제시하면 됨).

  | | access token | 웹 세션 ID |
  |---|---|---|
  | 쓸 수 있는 범위 | 해당 API | 그 사이트 전체 |
  | 수명 | 몇 분 | 로그아웃·만료까지, 쓰면 계속 연장 |
  | 유출 시 | 곧 못 쓰게 됨 | 사용자가 로그아웃할 때까지 유효 |

  - 값이 다른 서버들로 나가면 그 서버의 침해, 로그·DB 기록, 평문(HTTP) 구간이 모두 유출 경로가 된다.
- **대신 호출하는 서버가 있으면 검증 수단이 달라진다**
  - 서버 저장 세션(세션 ID로 서버 DB를 조회)은 누가 어느 IP에서 들고 오든 존재·만료·로그아웃 여부를 확인할 수 있다.
  - 쿠키 안에 사용자 정보와 IP를 암호화해 넣고 요청 IP와 비교하는 방식은, 다른 서버가 대신 호출하면 IP가 달라 통과할 수 없다. IP 검사를 빼면 로그아웃 후에도 통하는 만료 없는 열쇠가 된다.
  - 서버가 받은 값이 "사용자 브라우저의 쿠키와 같은지"를 직접 비교할 수는 없다. 그 요청에는 브라우저 쿠키가 실려 오지 않는다. 할 수 있는 확인은 "살아 있는 세션으로 존재하는가"이고, 들고 온 쪽이 정당한지는 구분하지 못한다.
- **더 안전한 대안(전용 불투명 토큰)**: 서버가 임의 문자열을 만들어 세션과 짝지어 저장하고, 외부에는 그 문자열만 넘긴다. API는 그 문자열로 짝지어진 세션이 살아 있는지 확인한다. 유출돼도 해당 API만 호출할 수 있고 화면 로그인에는 쓸 수 없으며, 로그아웃하면 함께 무효가 된다.
- **"주인이 누구인가"와 "지금 유효한가"는 다른 확인이다**: 쿠키를 복호화해 사용자 정보를 돌려주는 유틸리티는 보통 앞의 것만 한다. API 인증에 재사용하려면 만료 검사, 허용 형식 제한, 권한 변경 여부 확인을 따로 더해야 한다.

## 예시
```bash
# 인증만 따로 시험: 중간 서버를 거치지 않고 API를 직접 호출
curl -i -H "Authorization: Bearer <토큰>" https://example.com/api/me

# 상대 서버가 어떤 인증을 요구하는지: 401 응답의 WWW-Authenticate 헤더를 본다
curl -i -X POST -H "Content-Type: application/json" -d "{}" https://example.com/api/check
```

## 주의할 점
- 본문이 비어 있는 401은 대개 애플리케이션 로직에 들어가기 전, 인증 미들웨어 단계에서 걸러진 응답이다. 헤더 이름·인증 모드 설정 불일치를 먼저 의심한다.
- 인증 방식을 옵션으로 둘 때 "A가 아니면 B"로 분기하면 세 번째 방식이 들어올 때 깨진다. enum으로 방식을 직접 비교하고, 모르는 값의 기본 동작(오타 포함)을 문서화한다.
- 세션 ID를 외부로 넘겨야 한다면 전 구간 HTTPS와 수신 측 로그 미기록이 가장 효과가 크다.
- 세션 쿠키에 HttpOnly가 없으면 페이지 스크립트가 읽을 수 있어, XSS 하나로 세션을 뺏긴다.
