# 성능 측정값이 튈 때 측정 밖 부하 가려내기

> 분류: 기타 · 최근 갱신: 2026-11-11

## 한 줄 요약
화면 응답 시간을 3회 평균으로 잴 때 한 회차만 2~4초로 튀면, 그 페이지 문제로 단정하지 말고 같은 시각의 외부 사건(망 전환, 다른 작업의 서버 재기동·재컴파일, 같은 DB를 쓰는 다른 측정, 메모리 스왑)과 시각을 맞춰 본다. 원인을 찾으면 측정 스크립트가 그 사건을 감시해 겹친 회차를 버리고 다시 재게 한다.

## 내용
- 튐의 모양: 같은 페이지가 늘 느린 게 아니라 그때그때 다른 페이지의 한 회차만 튄다 → 측정 밖 부하 가능성이 크다. 다시 재서 정상 범위로 돌아오면 확인된다. 다시 재도 같은 값이면 실제로 느린 화면이다.
- 시각 맞추기: 서버 접근 로그의 요청 시각과 사건 기록(망 전환 로그, 서버 기동·종료 로그, 클래스 컴파일 시각, 다른 측정의 실행 시각)을 나란히 놓는다. 예: 튄 10건이 모두 망 전환과 몇 초 안으로 겹쳤고, 전환이 없는 회차는 정상이었다.
- 공용 측정 환경의 함정
  - 여러 사람·여러 자동화 세션이 같은 테스트 서버와 DB를 쓰면 한쪽의 재기동·재컴파일·대량 데이터 작업이 다른 쪽 측정을 오염시킨다. 측정 전에 순서를 맞추고, 별도 포트로 서버를 띄워도 DB는 하나라 DB 부하는 섞인다.
  - PC 여유 메모리가 적은 상태에서 서버를 더 띄우면 스왑으로 모든 응답이 느려진다. 띄우기 전에 여유 메모리를 본다.
  - 측정 대상에 닿지 않는 외부 서버(메일·SSO·AI 권한 확인) 대기가 끼면 그 구간을 빼거나 미리 불러 측정값에서 분리하고 비고에 적는다.
- 보고 방식: 원래 평균을 지우지 말고 "재측정 값으로 교체, 원래 평균·최대값"을 비고에 남긴다. 평균만 보면 튄 한 회차가 판정을 바꾼다. 필요하면 5회 재서 최솟값·최댓값을 뺀 평균(또는 중앙값)을 쓴다.
- "화면에 목록이 보이는 시간"과 "모든 요청이 끝난 시간"을 따로 기록한다. 개선 효과가 어느 쪽인지 갈린다.

## 핵심 코드
### 1) 측정 중 Wi-Fi 연결 감시 (Windows, Node.js)
```javascript
const { execSync } = require("child_process");
const events = [];                         // [{t, ssid}]
let last = null, timer = null;
function startNetWatch() {
  timer = setInterval(() => {
    let ssid = "";
    try { ssid = (execSync("netsh wlan show interfaces").toString().match(/^\s*SSID\s*:\s*(.+)$/m) || [])[1] || ""; } catch (e) {}
    if (ssid !== last) { events.push({ t: Date.now(), ssid }); last = ssid; }
  }, 500);
}
function stopNetWatch() { clearInterval(timer); timer = null; }   // 종료 뒤 다시 걸리지 않게 확실히 해제
function overlapsSwitch(start, end) {      // 구간 앞 10초 ~ 뒤 3초에 전환이 있었나
  return events.some(e => e.t >= start - 10000 && e.t <= end + 3000);
}
```

### 2) 겹친 회차는 버리고 다시 재기
```javascript
async function measure(item) {
  for (let attempt = 1; attempt <= 3; attempt++) {
    const start = Date.now();
    const ms = await runScenario(item);    // 화면 열기 ~ 요청이 모두 끝나고 0.3초 변화 없음
    if (!overlapsSwitch(start, Date.now())) return { ms, retried: attempt - 1 };
  }
  return { ms: null, note: "망 전환과 계속 겹침" };
}
```

## 주의할 점
- 감시 루프를 멈출 때 마침 실행 중인 콜백이 다시 타이머를 거는 구조면 프로세스가 끝나지 않고 계속 돌며 다음 측정에 부하를 준다. 정지 플래그를 두고 콜백 안에서도 확인한다.
- 튄 원인을 확인하지 않은 채 "측정 잡음"이라고만 적지 않는다. 시각 대조로 근거를 남긴다.
