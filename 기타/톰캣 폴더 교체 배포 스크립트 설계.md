# 톰캣 폴더 교체 배포 스크립트 설계

> 분류: 기타 · 최근 갱신: 2026-11-05

## 한 줄 요약
war를 운영 폴더에 바로 풀지 않고 작업 폴더에 준비해 둔 뒤, 톰캣을 내린 짧은 구간에 폴더만 바꿔 끼우면 중단 시간이 짧고 되돌리기가 쉽다.

## 내용
- **준비와 교체를 나눈다**
  - 준비(운영 영향 없음): 작업 폴더에 war를 풀고, 공유 저장소 심볼릭 링크를 걸고, 운영 설정 파일을 가져온다.
  - 교체(중단 구간): 톰캣 내리기 → 이전 보관본 삭제 → 운영 폴더를 `.old`로 이동 → 새 폴더를 운영 위치로 이동 → 톰캣 올리기.
  - 사람의 확인(설정 비교 등)은 두 단계 사이에 둔다. 그 전에 어디서 멈추든 운영 폴더는 그대로다.
- **"준비 완료" 표시 파일**: 준비가 끝까지 성공했을 때만 빈 파일을 만들고, 교체 단계는 그 파일이 없으면 거부한다. "폴더가 있는가"로 판단하면, 중간에 실패해 반쯤 만들어진 폴더가 운영으로 올라간다.
- **설정 파일 다루기**: war 안의 설정은 개발 PC 기준 값이므로 운영에서 쓰던 파일을 기본으로 깐다. 덮어쓰기 전에 war 원본을 다른 이름으로 남겨 두면 "새 버전에만 있는 항목"을 비교할 수 있다. 비교는 항목 이름 기준으로 하고, 값만 다른 항목은 운영 값을 유지한다.
- **동시 실행 막기**: `mkdir 잠금폴더`가 성공하면 진행, 실패하면 다른 작업이 진행 중으로 본다. `mkdir`은 "없으면 만들고 있으면 실패"가 한 번에 일어나서 잠금으로 쓸 수 있다. `trap '…' EXIT`로 끝날 때 지운다. 남아 버리면 `rmdir`로 지운다(빈 폴더만 지우므로 안전).
- **톰캣이 떠 있는지 판별**: `startup.sh`는 JVM을 띄우고 바로 끝나므로 프로세스 목록에는 `java`만 남는다. 프로그램 이름이 `java`이고 명령줄에 그 톰캣의 `-Dcatalina.base=` 경로가 들어 있는지로 판별한다. 같은 로그를 `tail`하는 프로세스처럼 경로만 겹치는 것을 톰캣으로 착각하지 않게 프로그램 이름도 함께 본다.
- **기동 완료 확인의 함정**: 로그에서 `Server startup in` 문구를 기다리는 방식은 JVM 로캘에 따라 문구가 번역되어 찍히거나, 로그가 다른 파일로 가는 설정이면 영영 잡히지 않는다. 포트에 직접 요청을 보내 응답을 보는 쪽이 설정에 흔들리지 않는다. 확인을 아예 사람에게 맡긴다면 기동 직후 로그를 자동으로 띄워 준다.
- **되돌리기**: `.old`를 운영 위치로 다시 올린다. 운영 폴더를 바로 지우지 말고 잠깐 옮겼다가, 이전 버전 이동이 성공한 뒤에 지운다. 이동이 실패하면 옮겨 둔 폴더를 되돌려 놓을 수 있다. DB 변경과 공유 저장소의 파일은 되돌아가지 않는다.
- **삭제 범위 제한**: 스크립트가 지울 수 있는 곳을 작업 폴더 아래로 한정한다. 운영 폴더를 지워야 하면 작업 폴더로 옮긴 뒤 지운다.
- **JSP 컴파일 캐시(`work/Catalina/localhost/<컨텍스트>`) 지우기**: 톰캣(Jasper)은 JSP를 처음 열 때 `.java`·`.class`로 컴파일해 여기에 두고, 정상 종료 때 세션을 `SESSIONS.ser`로 저장한다. 보통은 JSP와 class의 수정 시각을 비교해 다시 컴파일하지만 설정(`development=false` 등)에 따라 옛 class를 쓸 수 있고, 새 버전 클래스로 옛 세션을 되살리다 역직렬화 오류가 날 수 있다. 교체 뒤 시작 전에 지우면 둘 다 막는다. 대가는 각 화면 첫 접속 때 한 번 재컴파일로 조금 느린 것뿐이다.
- **`pgrep -f`의 범위**: `-f`는 명령줄 전체에서 찾으므로 `/app`처럼 짧은 경로는 그 경로의 로그를 `tail -f`하는 프로세스도 잡는다. 톰캣이 내려가도 "아직 떠 있음"으로 보여 종료 대기 실패가 난다. `catalina.base=<톰캣 경로>`처럼 톰캣만 갖는 문자열로 좁히고, 실제 값이 같은지(끝의 `/`, 심볼릭 링크 경로) `ps -ef | grep catalina.base`로 확인한다.
- **외부 환경변수에 기대는 경로**: 기존 스크립트가 서버 계정의 환경변수(예: 배포 기준 경로)를 선언 없이 쓰는 경우가 있다. 비어 있으면 `$BASE/app`가 `/app`이 되어 루트 아래를 만들거나 지운다. 스크립트 맨 위에서 선언하거나 `${BASE:?}`로 빈 값을 막는다.
- **종료가 늦는 톰캣**: 애플리케이션의 스케줄러 스레드(비데몬) 때문에 `shutdown.sh`만으로 몇십 초 안에 안 내려가는 경우가 흔하다. 대기 횟수를 넉넉히 두고, 그래도 남으면 `kill`(TERM)을 보내고 최후에만 `kill -9`를 쓴다.
- **war 풀기·설정 복사를 내리기 전에**: 준비를 서버를 내리기 전에 하면 중단 시간이 줄고, war가 깨졌을 때 서버를 내리지 않고 멈출 수 있다. 앞 단계가 실패해도 시작 명령이 항상 실행되는 구조(`;`로 잇기)는 `&&`나 `set -e`로 바꾼다.

## 핵심 코드

### 1) 동시 실행 잠금과 톰캣 프로세스 찾기
```bash
set -euo pipefail                     # 실패하면 즉시 중단, 미정의 변수는 오류

LOCK_DIR="$TOMCAT_HOME/.deploy.lock"
if ! mkdir "$LOCK_DIR" 2>/dev/null; then
    echo "다른 배포가 진행 중입니다." >&2; exit 1
fi
trap 'rmdir "$LOCK_DIR" 2>/dev/null || true' EXIT

# 이 톰캣의 java 프로세스 찾기
ps -e -o pid= -o comm= -o args= \
  | awk -v home="$TOMCAT_HOME" '$2 == "java" && index($0, home) { print $1 }'
```

### 2) 준비 단계 (운영 영향 없음)
```bash
# 변수 예: TOMCAT_HOME=/opt/tomcat  APP_DIR=$TOMCAT_HOME/webapps/ROOT  WORK_DIR=/opt/deploy  WAR=/opt/deploy/app.war
STAGE="$WORK_DIR/stage/ROOT"
rm -f "$WORK_DIR/stage/.ready"
rm -rf "${WORK_DIR:?}/stage/ROOT"                 # :? → 변수가 비면 중단(엉뚱한 곳 삭제 방지)
mkdir -p "$STAGE"
(cd "$STAGE" && unzip -q "$WAR")                  # unzip 이 없으면 jar xf "$WAR"
ln -s /shared/upload "$STAGE/upload"              # 공유 저장소 링크 (대상 끝에 / 붙이지 않음)
CONF=WEB-INF/classes/app.properties               # 바꿔야 할 곳: 운영 설정 파일 위치
cp "$STAGE/$CONF" "$WORK_DIR/stage/app.properties.from-war"   # war 원본은 비교용으로 남긴다
cp "$APP_DIR/$CONF" "$STAGE/$CONF"                # 운영에서 쓰던 설정을 깐다
touch "$WORK_DIR/stage/.ready"                    # 끝까지 성공했을 때만 표시 파일
```

### 3) 새 버전에만 있는 설정 항목 찾기 (이름 기준)
```bash
keys() { grep -vE '^[[:space:]]*(#|$)' "$1" | cut -d= -f1 | sed 's/[[:space:]]*$//' | sort -u; }
# 운영 설정에는 없고 war 원본에만 있는 키 → 운영 값으로 채워 넣어야 할 항목
comm -13 <(keys "$APP_DIR/$CONF") <(keys "$WORK_DIR/stage/app.properties.from-war")
```

### 4) 교체 단계 (중단 구간)
```bash
find_pids() { ps -e -o pid= -o comm= -o args= | awk -v home="$TOMCAT_HOME" '$2 == "java" && index($0, home) { print $1 }'; }

[ -f "$WORK_DIR/stage/.ready" ] || { echo "준비가 끝나지 않았습니다." >&2; exit 1; }
"$TOMCAT_HOME/bin/shutdown.sh" || true
for n in $(seq 1 30); do [ -z "$(find_pids)" ] && break; sleep 2; done
[ -z "$(find_pids)" ] || { echo "톰캣이 내려가지 않았습니다." >&2; exit 1; }

rm -rf "${WORK_DIR:?}/old"                         # 이전 보관본 삭제는 작업 폴더 안에서만
mv "$APP_DIR" "$WORK_DIR/old"
mv "$WORK_DIR/stage/ROOT" "$APP_DIR"
rm -f "$WORK_DIR/stage/.ready"
"$TOMCAT_HOME/bin/startup.sh"
```

### 5) 기동 확인 (로그 문구 대신 포트 응답)
```bash
for n in $(seq 1 60); do
  code=$(curl -s -o /dev/null -w '%{http_code}' "http://localhost:8080/" || true)   # 연결 실패면 000
  if [ "$code" != "000" ]; then echo "응답 코드 $code"; break; fi
  sleep 2
done
```

### 6) JSP 캐시 삭제와 좁힌 프로세스 검색
```bash
: "${DEPLOY_BASE:?DEPLOY_BASE가 비어 있습니다}"     # 바꿀 곳: 외부에서 받는 기준 경로
TARGET="catalina.base=$TOMCAT_HOME"                  # tail -f 같은 다른 프로세스가 안 잡히게
"$TOMCAT_HOME/bin/shutdown.sh"
for n in $(seq 1 30); do pgrep -f "$TARGET" >/dev/null || break; sleep 2; done
pgrep -f "$TARGET" >/dev/null && { echo "서버종료 실패" >&2; exit 1; }
# ... 폴더 교체 ...
rm -rf "$TOMCAT_HOME/work/Catalina/localhost/ROOT"  # 바꿀 곳: 컨텍스트 이름
"$TOMCAT_HOME/bin/startup.sh"
```

### 7) 되돌리기
```bash
"$TOMCAT_HOME/bin/shutdown.sh" || true             # (4번처럼 프로세스가 사라질 때까지 기다린다)
mv "$APP_DIR" "$WORK_DIR/failed"                   # 바로 지우지 않고 잠깐 옮긴다
if mv "$WORK_DIR/old" "$APP_DIR"; then
  find "$WORK_DIR/failed" -type l -exec unlink {} \;   # 링크를 먼저 끊고
  rm -rf "${WORK_DIR:?}/failed"                       # 그다음 삭제
else
  mv "$WORK_DIR/failed" "$APP_DIR"                 # 이전 버전 이동 실패 → 원위치
fi
"$TOMCAT_HOME/bin/startup.sh"
```

## 주의할 점
- `ps -eo pid=,comm=,args=`처럼 쉼표로 이어 쓰면 `=` 뒤를 끝까지 첫 열의 제목으로 읽어 pid만 출력되는 경우가 있다. 그러면 떠 있는 톰캣을 "없음"으로 판단해 내리지 않고 폴더를 바꾸게 된다. 열마다 `-o`를 따로 준다.
- 가짜 명령으로 만든 로컬 테스트는 이런 실제 환경의 차이를 드러내지 못한다. 프로세스 판별처럼 위험한 부분은 대상 환경에서 읽기 전용 명령으로 먼저 확인한다.
- 심볼릭 링크가 들어 있는 폴더를 지울 때는 링크를 먼저 `unlink`로 끊는다. 지우는 방식에 따라 링크가 가리키는 실제 파일이 지워질 수 있다. `ln -s`로 링크를 만들 때 대상 경로 끝에 `/`를 붙이지 않는다.
- `docker cp`는 계정 옵션이 없어 복사된 파일이 root 소유가 되고, 셸을 거치지 않아 `~`를 홈으로 바꾸지 않는다. 컨테이너 안 경로는 전체 경로로 적는다.
- 이름이 `~`인 폴더가 실수로 생겼다면 `rm -rf './~'`로 지운다. `rm -rf ~`는 홈 폴더 전체를 지운다.
- 빌드 도구가 현재 작업 폴더 상태 그대로 빌드한다면 커밋하지 않은 수정과 다른 브랜치도 그대로 배포된다. 배포 전에 `git status`와 `git log -1 --oneline`을 확인한다.
