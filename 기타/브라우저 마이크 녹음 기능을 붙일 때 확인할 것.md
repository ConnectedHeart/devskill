# 브라우저 마이크 녹음 기능을 붙일 때 확인할 것

> 분류: 기타 · 최근 갱신: 2026-10-16

## 한 줄 요약
웹(특히 모바일 웹·하이브리드 앱)에 실시간 녹음을 붙일 때는 코드보다 환경 조건이 먼저 막힌다. https, 앱 웹뷰의 마이크 권한, 프록시의 WebSocket 업그레이드, 다중 서버의 고정 세션을 먼저 확인해야 한다.

## 내용
### 브라우저·앱 조건
- `getUserMedia`(마이크)는 보안 컨텍스트, 즉 https나 localhost에서만 동작한다. http 운영 주소에서는 권한 창조차 뜨지 않는다. 이때는 "이 기기에서 녹음할 수 없음" 같은 안내를 띄운다.
- 하이브리드 앱이면 웹뷰가 페이지에 마이크 권한을 넘겨줘야 한다(안드로이드 `onPermissionRequest`, 앱 매니페스트 권한). 이것은 웹 코드로 해결할 수 없어 앱 쪽 작업이 필요하다.
- 녹음 중 화면을 닫거나 뒤로 가면 `MediaStreamTrack.stop()`으로 마이크를 끄고 소켓을 닫는다. 이 처리가 없으면 화면을 떠난 뒤에도 녹음이 계속 살아 있는 경우가 있다.

### 실시간 전송 구조
- 브라우저 → 화면 서버 → 내부 API 서버 → 음성인식 서버처럼 여러 단을 WebSocket으로 중계할 때가 많다. 각 단의 송신은 전용 스레드·큐로 처리하고, 큐가 밀리면 오래된 조각을 버리는 정책을 정해 둔다. 그래야 한 단이 느려도 전체가 멈추지 않는다.
- WebSocket 핸드셰이크에서는 쿠키나 IP 같은 기존 인증 수단을 쓰기 어려운 경우가 있다. 그럴 때는 인증된 REST 호출로 **짧은 수명(예: 1분)의 1회용 티켓**을 발급받아 연결 시 제출하게 한다. 티켓을 암호화만 하고 무결성 값(HMAC 등)을 붙이지 않으면 위변조 검증이 약해진다. 가능하면 서명을 붙이고, 최소한 형식 검사와 만료 검사는 한다.
- 녹음 기능은 PC와 모바일이 같은 중계 로직을 쓰도록 공용 클래스로 뺀다. 그래야 종료 순서나 오류 처리가 어긋나지 않는다.

### 운영 환경
- 앞단 프록시(웹서버, L7)에서 해당 경로의 `Upgrade: websocket`을 허용해야 한다. 유휴 타임아웃이 짧으면 녹음 중에 끊긴다.
- 서버가 여러 대이면, 연결이 유지되는 동안 같은 서버로 가도록 L4/L7에서 고정 세션(sticky)을 설정해야 할 수 있다.

## 주의할 점
- 일시중지 시 자동 임시저장 같은 기능은 "녹음 파일이 실제로 생겼는지" 서버에 확인한 뒤 저장해야 빈 기록이 남지 않는다.
- 모바일 브라우저마다 지원하는 오디오 코덱이 다르다. 재생까지 고려하면 서버에서 범용 형식으로 저장한다.
