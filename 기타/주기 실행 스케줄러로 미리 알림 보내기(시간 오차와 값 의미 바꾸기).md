# 주기 실행 스케줄러로 미리 알림 보내기(시간 오차와 값 의미 바꾸기)

> 분류: 기타 · 최근 갱신: 2026-11-18

## 한 줄 요약
"N분 전 알림"을 주기 스케줄러가 "지금 ~ 지금+주기" 창으로 골라 보내는 구조에서는 알림이 최대 주기만큼 일찍 간다. 짧은 옵션(10분 등)을 추가하려면 주기를 줄여야 하고, "0=사용안함"처럼 이미 저장된 값의 뜻을 바꿀 때는 데이터 변환을 코드 배포와 정확히 한 번 맞춰야 한다. 원본 행에서 파생 행을 만들 때 부모 키를 잘못 넣으면 수정·삭제가 파생 행에 전파되지 않는다.

## 내용
### 창(window) 방식의 오차
- 스케줄러가 주기 P마다 돌며 `알림 시각 = 시작 - 리드타임`이 `[지금, 지금+P)` 안에 드는 일정을 보낸다.
- 알림은 창의 시작 시각(스케줄러가 돈 시각)에 나가므로 최대 P만큼 일찍 간다. 예: P=30분, 10:25 일정의 "10분 전"(10:15) 알림은 10:00 실행에서 잡혀 25분 일찍 간다.
- 옵션의 최소 리드타임보다 P가 충분히 작아야 의미가 있다. 10·20분 옵션이면 P=5분 정도.
- 창 길이를 코드에 따로 박지 말고 cron 주기와 같은 값을 쓰게 하면, 주기를 바꿔도 누락·중복이 생기지 않는다.
- "즉시(시작 시각)"는 리드타임 0이다. 정각 일정은 정확히 가고, 정각이 아닌 일정은 직전 실행 시각에 간다.

### 저장된 값의 뜻 바꾸기 (예: 사용안함 0 → -1, 즉시 0)
- 코드만 바꾸면 기존에 "사용안함(0)"을 고른 사람이 모두 "즉시"가 되어 알림이 쏟아진다.
- 함께 해야 할 것: 기존 데이터 변환(`0 → -1`)을 배포와 같은 시점에 한 번만, 컬럼 기본값 변경, 조건문(`<> 0`) 전부 수정, 설정 행을 새로 만드는 코드의 기본값.
- 되돌릴 때도 데이터를 역변환해야 한다. 여러 사이트에 배포한다면 변환 SQL을 패치에 같이 넣는다.
- 대안: 기존 값은 두고 새 옵션에 다른 값(예: 1분)을 써서 "즉시"로 표시하면 데이터 변환이 필요 없다. 값의 자연스러움과 배포 위험을 비교해 고른다.
- 변환 SQL은 두 번 돌려도 결과가 같게(두 번째 실행은 0행) 쓰고, 트랜잭션 안에서 실행해 행 수를 본 뒤 롤백하는 시험을 먼저 한다.

### 파생 행의 부모 키
- 원본 일정에서 참석자별 알림 행처럼 파생 행을 만들 때, 파생 행의 "부모" 컬럼에 원본 ID 대신 원본의 부모 값(최상위면 0)을 그대로 복사하는 실수가 흔하다.
- 수정·삭제·참석자 제외 쿼리가 `parent_id = 원본 ID`로 파생 행을 찾으면 그 행만 남아, 시간을 바꿔도 옛 시각에 발송되고 삭제·제외 뒤에도 발송된다.
- 고친 뒤에는 이미 잘못 들어간 행을 원본에 맞추고, 원본이 없는 행을 지우는 보정 SQL이 필요하다.

### 설정 행이 없는 사용자에게 기본값 쓰기
- 사용자별 설정 테이블 행이 사용자 생성 때가 아니라 "설정을 처음 저장할 때" 생기면, 저장한 적 없는 사용자는 `INNER JOIN` 발송 쿼리에서 빠져 알림을 전혀 받지 못한다. 설정 화면에서도 첫 선택지("사용 안 함")로 보이고, `UPDATE`로 일괄 변경해도 행이 없어 바뀌지 않는다.
- 해결: `LEFT JOIN` + `COALESCE(설정값, :기본값)`으로 바꾸고 기본값은 사이트 설정에서 읽는다. 키가 없으면 "사용 안 함"으로 두면 설정을 넣지 않은 사이트는 동작이 같다. 설정 화면도 행이 없을 때 기본값을 선택해 보여 주되, 화면을 열기만 해서 행을 만들지는 않는다.
- 행이 있으면 "사용 안 함"이라도 사용자 값을 우선한다. 다른 설정(메일 알림 등)을 저장하면서 행이 생길 때 "사용 안 함"을 넣는 코드가 있으면, 직접 고른 사람과 구별되지 않으므로 그 자리도 기본값을 넣게 바꾼다. 이미 들어간 값은 코드로 구별할 수 없어 운영 쪽이 정한다.
- 기본값은 화면 선택 목록에 있는 값으로 한다. 목록 밖 값(예: 45)은 발송은 되지만 선택칸이 비어 보인다.

### 시험 방법
- 실제 발송 시각은 기다려야 보인다. 시작 시각을 몇 분 뒤로 잡은 시험 일정을 경우별로 만들고, 스케줄러 주기를 줄여 띄운 뒤 발송 기록(알림 상태 컬럼, 가짜 알림 서버의 수신 기록)을 시각별로 판정한다.
- 경우표: 리드타임별 단독, 반복, 시작 시각 수정, 삭제, 사용안함, 참석자 수락 뒤 수정·삭제·제외, 미수락.
- 스케줄러가 여러 서버 중 한 대만 돌도록 선출 절차가 외부 서버에 걸려 있으면, 로컬에서는 그 호출에 성공을 돌려주는 가짜 서버를 띄운다.

## 핵심 코드
### 1) 창 방식 대상 조회 (MySQL)
```sql
-- :now = 스케줄러 실행 시각, :period = cron 주기(분)
SELECT e.event_id, u.user_id
  FROM events e
  JOIN user_settings u ON u.user_id = e.owner_id
 WHERE u.remind_minutes <> -1                              -- -1 = 사용안함
   AND e.start_time - INTERVAL u.remind_minutes MINUTE >= :now
   AND e.start_time - INTERVAL u.remind_minutes MINUTE <  :now + INTERVAL :period MINUTE
   AND e.remind_sent = '0';
```

### 1-1) 설정 행이 없으면 기본값 (MySQL)
```sql
-- :defaultMinutes = 사이트 설정 기본값(없으면 -1)
SELECT e.event_id, e.owner_id
  FROM events e
  LEFT JOIN user_settings u ON u.user_id = e.owner_id
 WHERE COALESCE(u.remind_minutes, :defaultMinutes) <> -1
   AND e.start_time - INTERVAL COALESCE(u.remind_minutes, :defaultMinutes) MINUTE >= :now
   AND e.start_time - INTERVAL COALESCE(u.remind_minutes, :defaultMinutes) MINUTE <  :now + INTERVAL :period MINUTE;
```

### 2) 주기와 창 길이를 같은 설정에서
```java
@Scheduled(cron = "${app.cron.remind:0 0/5 * * * *}")
public void sendReminders() {
    int periodMinutes = cronPeriodMinutes(remindCron);   // 창 길이를 cron에서 계산
    reminderService.sendDue(LocalDateTime.now(), periodMinutes);
}
```

### 3) 값 의미 변환 (배포 때 한 번)
```sql
ALTER TABLE user_settings ALTER remind_minutes SET DEFAULT '-1';
UPDATE user_settings SET remind_minutes = '-1' WHERE remind_minutes = '0';  -- 두 번째 실행은 0행
```

### 4) 파생 행 생성 때 부모 키
```java
Reminder r = new Reminder();
r.setEventId(attendeeEventId);
r.setParentId(originalEventId);   // 원본의 parentId가 아니라 원본 ID 자체
r.setStartTime(original.getStartTime());
reminderDao.insert(r);
```

### 5) 기존 파생 행 보정
```sql
UPDATE reminders r JOIN events e ON e.event_id = r.event_id
   SET r.parent_id = e.parent_id, r.start_time = e.start_time,
       r.sent = CASE WHEN r.start_time <> e.start_time THEN '0' ELSE r.sent END
 WHERE r.parent_id = 0 AND e.parent_id <> 0;

DELETE r FROM reminders r LEFT JOIN events e ON e.event_id = r.event_id
 WHERE e.event_id IS NULL;
```

## 주의할 점
- 주기를 줄이면 스케줄러 실행 횟수가 늘어난다. 대상 조회 쿼리가 인덱스를 타는지 확인한다.
- 자정을 넘는 리드타임(00:05 일정의 10분 전)은 날짜 경계 계산이 맞는지 따로 본다.
- 여러 테넌트를 도는 루프에서 대상이 없는 테넌트를 만나 `return`하면 뒤쪽 테넌트가 처리되지 않는다. `continue`인지 확인한다.
- 다중 서버에서는 스케줄러가 한 대만 돌게 하는 선출 장치가 있어야 같은 알림이 중복 발송되지 않는다.
- 실행이 늦게 시작하면(예: 16:25 실행이 16:26에 시작) 그 창의 알림을 건너뛸 수 있다. 창 시작을 "지금"이 아니라 "직전 실행이 처리한 끝 시각"으로 잡거나, 시험할 때 실행 지연이 없는지 먼저 본다.
