# 파일 경로만 넘기는 서버 간 연동과 공유 저장소

> 분류: 기타 · 최근 갱신: 2026-10-19

## 한 줄 요약
애플리케이션 서버가 파일 내용 대신 **경로만** 다른 서버(음성 인식·변환 서버 등)에 넘기는 구조라면, 두 서버가 같은 저장소를 같은 경로로 봐야 한다. 공유가 깨지면 오류 대신 "빈 결과"가 정상 응답으로 돌아와 원인을 찾기 어렵다.

## 내용
- 큰 파일을 HTTP로 다시 보내지 않으려고 `/files/upload/<파일>` 같은 상대 경로만 넘기고, 받는 서버가 자기 쪽 마운트에서 그 경로를 연다. 반대로 외부 서버가 결과 파일을 직접 써 두면 애플리케이션 서버가 그 경로에 파일이 생겼는지 폴링하기도 한다.
- 공유가 안 되면 나타나는 증상
  - 받는 서버가 파일을 못 찾아도 HTTP 200에 빈 배열·길이 0을 돌려준다. 화면은 이것을 "지원하지 않는 파일"로 오판한다.
  - 처리 시간이 비정상적으로 짧다(수십 ms). 파일 형식과 무관하게 모두 같은 결과가 나온다.
  - 외부 서버가 쓴 결과 파일이 애플리케이션 서버에서 끝까지 보이지 않아 폴링이 시간 초과된다.
- 원인 후보: 공유 디렉터리(NFS 등) 마운트 누락, 두 서버의 기준 경로 설정 차이, 파일을 만든 계정과 읽는 계정의 권한 차이.
- **로컬 개발 서버**는 파일을 개발 PC 디스크에 저장하므로, 원격 처리 서버를 연결해도 이 기능은 구조적으로 끝까지 시험할 수 없다. 코드 결함으로 오해하지 않는다.
- 이중화(서버 여러 대) 환경에서는 처리 서버와 모든 WAS가 같은 공용 저장소를 봐야 한다.

## 예시
```bash
# 양쪽 서버에서 같은 파일이 같은 크기·권한으로 보이는지
ls -l <공유 루트>/files/upload/<파일>
# 마운트 확인
mount | grep <공유 루트>
df -h <공유 루트>
```

## 주의할 점
- 외부 서버 응답 본문을 로그에 남기지 않으면 "왜 비었는지"를 알 수 없다. 길이·상태 코드와 함께 짧은 응답 요약을 디버그 로그로 남기는 것이 좋다.
- 경로를 넘길 때는 상대 경로를 쓰고, 받는 쪽이 허용된 루트 밖을 열지 않도록 검증한다(경로 조작 방지).
