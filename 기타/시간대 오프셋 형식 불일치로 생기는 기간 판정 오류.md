# 시간대 오프셋 형식 불일치로 생기는 기간 판정 오류

> 분류: 기타 · 최근 갱신: 2026-10-27

## 한 줄 요약
시간 변환 함수가 기대하는 시간대 문자열 형식과 호출자가 넘기는 형식이 다르면, 함수가 조용히 변환을 건너뛰고 UTC를 돌려줘 "지금 기간 안인가" 판정이 시차만큼 틀어진다.

## 내용
- 사내 공통 함수가 `"<이름>|+09:00"`처럼 자체 형식만 받도록 만들어져 있고, 형식이 맞지 않으면 예외 없이 원래 값(UTC)을 그대로 돌려주는 경우가 있다.
- 새 API(외부 연동, AI용 API 등)는 표준 형식인 `"+09:00"`이나 `"Asia/Seoul"`을 넘기기 쉽다. 그러면 변환이 일어나지 않고, 저장된 기간(현지 시각)과 현재 시각(UTC)을 비교하게 된다.
- 증상: 한국 14:16(UTC 05:16)에 14:00~15:00 설정이 "기간 밖"으로 판정된다. 같은 데이터를 쓰는 기존 화면은 정상이라 "새 기능만 틀린다"로 보인다.

### 고치는 방법
- 현재 시각 계산을 한 메소드로 모으고, 입력 시간대 값을 공통 함수가 기대하는 형식으로 정규화한 뒤 기존 화면과 **같은 함수·같은 방식**으로 비교한다.
- 가능하면 표준 API(`java.time.ZoneOffset.of("+09:00")`, `ZoneId.of("Asia/Seoul")`)로 바꾸되, 기존 기능과 판정이 어긋나지 않는지 확인한다.

## 핵심 코드

### 1) 자체 형식으로 정규화
```java
// 입력 형식 정규화 예 (사내 형식이 "id|+09:00"일 때)
static String normalizeTz(String tz) {
    if (tz == null || tz.isEmpty()) return "|+09:00";
    return tz.contains("|") ? tz : "|" + tz;
}
```
단위 테스트에는 세 가지를 넣는다: 형식 변환, UTC→현지 변환과 기간 판정, 그리고 **수정 전 방식으로는 기간 밖으로 판정되는 대조 케이스**(버그 재현).

### 2) 표준 API로 시간대 해석, 틀린 형식은 경고 (Java 8)
```java
static final ZoneId DEFAULT_ZONE = ZoneId.of("Asia/Seoul");      // 바꿔야 할 곳: 기본 시간대 정책

static ZoneId toZone(String tz) {
    String v = (tz == null) ? "" : tz.trim();
    if (v.contains("|")) v = v.substring(v.indexOf('|') + 1);    // "id|+09:00" → "+09:00"
    if (v.isEmpty()) return DEFAULT_ZONE;
    try {
        return ZoneId.of(v);                                      // "+09:00", "Asia/Seoul", "Z" 모두 처리
    } catch (DateTimeException e) {
        log.warn("알 수 없는 시간대 값: {}", tz);                  // 조용히 UTC 로 넘어가지 않게
        return DEFAULT_ZONE;
    }
}
```

### 3) 기간 판정: "지금"을 주입받아 현지 시각으로 비교
```java
// 저장된 기간이 현지 시각(LocalDateTime)일 때. 끝 시각은 포함하지 않음
static boolean isActive(LocalDateTime start, LocalDateTime end, ZoneId zone, Clock clock) {
    LocalDateTime now = LocalDateTime.now(clock.withZone(zone));
    return !now.isBefore(start) && now.isBefore(end);
}
```

### 4) 단위 테스트: 형식별 판정 + 수정 전 방식 대조 (JUnit 4)
```java
@Test
public void kst1416IsInsideWindow() {
    Clock clock = Clock.fixed(Instant.parse("2026-01-05T05:16:00Z"), ZoneOffset.UTC);   // 한국 14:16
    LocalDateTime s = LocalDateTime.of(2026, 1, 5, 14, 0);
    LocalDateTime e = LocalDateTime.of(2026, 1, 5, 15, 0);

    assertTrue(isActive(s, e, toZone("+09:00"), clock));
    assertTrue(isActive(s, e, toZone("Asia/Seoul"), clock));
    assertTrue(isActive(s, e, toZone("id|+09:00"), clock));
    assertFalse(isActive(s, e, ZoneOffset.UTC, clock));   // 변환이 빠진 수정 전 방식: 기간 밖으로 판정(버그 재현)
}
```

## 주의할 점
- 형식이 틀렸을 때 조용히 원래 값을 돌려주는 함수는 버그를 숨긴다. 가능하면 경고 로그를 남기게 한다.
- 시간 관련 테스트는 "지금" 대신 고정 시각을 주입할 수 있게 만들어야 재현이 된다.
- 기간 판정 버그를 실제 API로 확인할 때는 "지금-5분 ~ 지금+60분"처럼 현재를 포함하는 기간을 잠깐 설정하고, 끝나면 원래 값으로 되돌린다. 원래 값을 읽는 응답 필드명을 잘못 짚으면 복원이 아니라 삭제가 되니 먼저 응답 구조를 확인한다.
