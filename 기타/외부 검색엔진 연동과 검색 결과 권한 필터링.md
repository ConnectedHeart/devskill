# 외부 검색엔진 연동과 검색 결과 권한 필터링

> 분류: 기타 · 최근 갱신: 2026-10-14

## 한 줄 요약
업무 시스템의 통합검색은 보통 외부 검색엔진이 DB 뷰를 읽어 색인하고, 앱은 질의만 중계한다. 권한 필터링은 "문서마다 볼 수 있는 주체 목록을 색인"하고 "사용자의 접근 식별자 목록"과 대조하는 방식으로 한다.

## 내용
- **역할 분담**: 앱은 검색어·영역·기간·페이지와 사용자 식별자만 검색엔진에 넘기고 결과를 화면에 그린다. 앱 안에는 색인 코드가 없을 수 있다.
- **색인 원천 제공**: DB에 검색엔진 전용 뷰를 만든다(문서 ID, 제목, 작성자, 날짜, 첨부 여부, 테넌트·회사, 본문 파일 경로 등). 본문이 파일로 저장되면 경로를 주고 엔진이 직접 읽는다. 진행 중·임시 상태 문서는 뷰 조건으로 제외한다.
- **증분 색인**: 대상 테이블에 트리거를 달아 등록·수정·삭제 시 `I/U/D` 이력 행을 별도 테이블에 쌓고, 엔진이 미처리 상태(`STATUS='N'` 같은) 행을 가져가 반영한 뒤 상태를 바꾼다.
- **권한 정보 색인**: 공유 대상(개인·부서·회사·직위·직책·권한그룹 등)을 사용자 단위로 펼친 권한 뷰를 제공하거나, 문서마다 "접근 가능한 주체" 목록을 색인한다. 검색 시 사용자 ID를 AND 조건으로 걸어 거른다.
- **접근 식별자 목록 방식**: 사용자 단위로 펼치는 대신, 문서에는 ACL 주체(`d:부서`, `g:그룹` 등)를 그대로 색인하고, 검색 시 "이 사용자가 속한 모든 주체" 목록(`u:`, `d:`, `c:`, `t:`, `p:`, `g:` 등 접두어 문자열 배열)을 받아 OR로 대조한다. 조직 변경 시 문서 재색인이 필요 없다는 장점이 있다. 이 목록을 주는 API를 만들 때는 앱의 실제 권한 판정 규칙(예: "하위 부서 포함" 등록, 여러 경로의 그룹 소속)과 똑같이 계산해야 검색 결과와 실제 열람 권한이 어긋나지 않는다.

## 예시
```json
{ "data": ["u:user1", "d:dept01", "c:comp01", "t:12", "p:34", "g:grpA", "g:grpB"] }
```
- 같은 그룹에 여러 경로로 속해도 `g:` 항목은 한 번만(DISTINCT).
- 값이 없는 종류는 항목 자체를 뺀다.

## 주의할 점
- 직위·직책 코드가 회사마다 겹치는 시스템이면 `t:코드@회사`처럼 범위를 붙여야 하고, 전역 고유 ID면 붙이지 않아도 된다. 같은 형식을 쓰는 서버가 여럿이면 형식을 맞춘다.
- 검색엔진 타임아웃과 재시도를 짧게 잡아 검색 장애가 화면 전체를 막지 않게 한다.
- 권한 판정 쿼리가 엔진 설정 쪽에만 있으면 앱 저장소만 보고는 규칙을 알 수 없다. 문서로 남긴다.
