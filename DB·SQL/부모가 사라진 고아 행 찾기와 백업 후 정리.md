# 부모가 사라진 고아 행 찾기와 백업 후 정리

> 분류: DB·SQL · 최근 갱신: 2026-11-10

## 한 줄 요약
FK 없이 ID 문자열로 부모를 가리키는 스키마에서는 부모 행만 지워진 "고아" 데이터가 생기고, 코드가 부모 조회 결과를 null 검사 없이 쓰면 그 화면만 500이 난다. 고아 범위를 LEFT JOIN으로 찾고, 딸린 테이블까지 세어 백업한 뒤 한 트랜잭션으로 지운다.

## 내용
- 증상: 같은 종류의 화면 여러 개 중 특정 항목 하나만 500이고, 스택은 부모 속성을 꺼내는 줄의 NullPointerException이다. 같은 코드가 다른 항목에서는 멀쩡하므로 코드가 아니라 데이터 차이를 의심한다.
- 원인: 부모(그룹, 상위 폴더 등) 행이 지워지거나 데이터 이관 때 빠졌는데 자식은 남았다. FK가 없으니 DB가 막아 주지 않는다.
- 찾기: 자식 테이블을 부모 테이블에 LEFT JOIN해서 부모가 NULL인 행을 고른다. 부모를 여러 컬럼(직속 부모, 최상위 그룹)으로 가리키면 각각 확인한다. 고아의 자식(손자)도 같이 범위에 든다.
- 정리 전에 확인할 것
  1. 정상 데이터가 고아를 부모로 가리키지 않는지(지우면 새 고아가 생긴다).
  2. 지울 범위가 딸린 테이블(권한, 글, 첨부 정보, 읽음 기록, 스크랩 등)까지 몇 행인지 표로 센다. 예상보다 훨씬 크면 지우기 전에 한 번 더 확인받는다.
  3. 다른 설정 테이블과 얽힌 행(화면 배치 등)은 따로 판단한다. 앱의 정상 삭제 기능도 남기는 행이라면 같이 남긴다.
  4. DB 행만 지우고 파일 저장소의 파일은 지우지 않는다(되돌리기 어렵다).
- 백업은 대상 행을 INSERT 문으로 떠 둔다. 되돌리기는 그 파일을 다시 실행하면 된다.
- 근본 대책은 코드의 null 검사(부모가 없으면 기본값으로 처리)다. 운영 데이터에도 고아가 있을 수 있으면 데이터 정리와 별개로 고친다.

## 핵심 코드
```sql
-- 1) 부모가 없는 자식 찾기
SELECT c.id, c.name, c.parent_id
FROM   folders c
LEFT JOIN folder_groups g ON g.id = c.group_id
WHERE  c.group_id IS NOT NULL AND g.id IS NULL;

-- 2) 지울 범위를 임시 테이블로 고정하고 딸린 테이블 행 수 세기
CREATE TEMPORARY TABLE orphan_ids AS
SELECT c.id FROM folders c LEFT JOIN folder_groups g ON g.id = c.group_id
WHERE c.group_id IS NOT NULL AND g.id IS NULL;

SELECT 'items' t, COUNT(*) FROM items WHERE folder_id IN (SELECT id FROM orphan_ids)
UNION ALL
SELECT 'folder_acl', COUNT(*) FROM folder_acl WHERE folder_id IN (SELECT id FROM orphan_ids);

-- 3) 고아 밖에서 고아를 가리키는 행이 없는지
SELECT COUNT(*) FROM folders
WHERE parent_id IN (SELECT id FROM orphan_ids) AND id NOT IN (SELECT id FROM orphan_ids);
```

```bash
# 4) 대상 행만 INSERT 문으로 백업 (MySQL/MariaDB)
mysqldump --no-create-info --skip-extended-insert mydb items \
  --where="folder_id IN ('<id1>','<id2>')" > orphan-backup.sql
```

```sql
-- 5) 한 트랜잭션으로 자식 → 부모 순서로 삭제 후 0건 확인
START TRANSACTION;
DELETE FROM items      WHERE folder_id IN (SELECT id FROM orphan_ids);
DELETE FROM folder_acl WHERE folder_id IN (SELECT id FROM orphan_ids);
DELETE FROM folders    WHERE id        IN (SELECT id FROM orphan_ids);
COMMIT;
```

```java
// 근본 대책: 부모 조회 결과 null 검사
FolderGroup group = groupDao.findById(folder.getGroupId());
String groupType = (group != null) ? group.getType() : "N"; // 부모 없으면 기본값
```

## 주의할 점
- MySQL에서 `DELETE ... WHERE id IN (SELECT ... FROM 같은 테이블)`은 막히므로 임시 테이블로 ID를 먼저 고정한다.
- 비교 컬럼의 문자셋·콜레이션이 다르면 조인 결과가 어긋날 수 있다. 결과 건수를 눈으로 한 번 확인한다.
- 삭제 후 지워진 항목을 예전 주소로 직접 열면 여전히 500일 수 있다(코드 null 검사가 없으면). 데이터 정리만으로 끝났다고 보지 않는다.
