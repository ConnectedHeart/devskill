# 페이징 목록 쿼리가 느린 원인과 개선 측정

> 분류: DB·SQL · 최근 갱신: 2026-11-09

## 한 줄 요약
"한 쪽 10건" 목록이 느릴 때는 쓰지 않는 조인이 행을 불리는지, 카운트 쿼리가 중복으로 도는지, 계산값·TEXT 열 정렬 때문에 전체를 정렬하는지를 먼저 보고, 첫째 정렬 열 경계로 범위를 좁히거나 뒤쪽 쪽을 역순으로 읽는 방법을 쓴 뒤, 수정 전후 쿼리를 같은 데이터에서 번갈아 재며 결과 해시까지 비교한다.

## 내용
### 흔한 원인
- **쓰지 않는 1:N 조인.** 조건을 주석 처리하면서 조인만 남은 경우, 문서 1건이 자식 행 수만큼 불어난 뒤 `SELECT DISTINCT`나 `COUNT(DISTINCT ...)`로 다시 합쳐진다. 결과는 같아서 눈치채기 어렵고 정렬·중복 제거 비용만 배로 는다. 걸러내는 조건 없는 LEFT JOIN이라 지워도 행이 줄지 않고, 그 테이블 컬럼을 참조하는 곳(별칭 없이 쓴 컬럼 포함)이 없는지만 확인하면 된다. 같은 테이블을 쓰는 서브쿼리가 자기 FROM으로 따로 조회하면 영향이 없다.
- **카운트 중복.** 화면이 목록 요청과 건수 요청을 나눠 보내도록 바꾸면서 서버의 목록 처리에서 카운트를 빼지 않으면, 한 화면에 카운트 쿼리가 두 번 돈다. 목록도 여전히 카운트가 끝나야 나와 분리 효과가 없다. 목록 요청에 "건수 생략" 플래그를 주고, 플래그를 보내지 않는 다른 호출처는 기존대로 둔다.
- **계산값 정렬 + DISTINCT 파생 테이블 + LIMIT.** 정렬 기준이 함수로 만든 값이면 인덱스를 못 쓰고, 조건에 맞는 전체 행을 넓은 컬럼째 임시 테이블에 넣어 정렬한 뒤 10건만 남긴다(`Using temporary; Using filesort`). varchar 컬럼이 많으면 임시 테이블이 디스크로 넘어간다.
- **조건이 가장 늦게 걸리는 조인 순서.** 부서 조건이 마지막 테이블에서야 걸리면 회사 전체를 읽고 행마다 조인한 뒤 걸러낸다. `ANALYZE`(MariaDB)/`EXPLAIN ANALYZE`(MySQL 8)의 테이블별 "읽은 행"과 "남긴 비율(filtered)"로 본다.

### 인덱스를 추가해도 안 빨라지는 경우
- 옵티마이저가 새 인덱스를 `possible_keys`에만 올리고 고르지 않을 수 있다. 측정 대상이 데이터가 가장 많은 부서라 선택도가 낮으면 기존 순서가 싸다고 판단한다. 통계 갱신(`ANALYZE TABLE`) 후에도 계획이 같으면 시간 차이는 측정 편차다.
- DDL 파일에는 있는데 운영·개발 DB에는 없는 인덱스가 있을 수 있다(신규 설치용 DDL에만 넣고 기존 사이트 패치 스크립트에 빠뜨림). `information_schema.STATISTICS`로 컬럼 구성 기준 대조한다.
- `STRAIGHT_JOIN`(MySQL·MariaDB)은 FROM에 적은 순서대로 읽게 강제하는 힌트다. 내부 조인 순서만 바뀌고 결과는 같다. "순서만 잘못 골랐는지, 읽을 방법(인덱스)이 없는지"를 읽기 전용으로 가려 보는 실험 도구로 쓰고, 코드에 고정하지 않는다(DB마다 힌트가 다르고, 분포가 다른 사이트에서는 더 느려질 수 있음).

### 2단계 페이징(지연 조인)
- 1단계에서 키와 정렬값만 뽑아 정렬·LIMIT하고, 2단계에서 그 10건에만 넓은 컬럼과 상세 조인을 붙인다.
- 위험: 한 키가 여러 행으로 나오는 조인(OR 조건 조인)이 있으면 1단계에서 합쳐져 행이 사라진다. 전체 행을 보고 계산하는 창 함수(`MAX() OVER`)는 2단계로 옮기면 값이 바뀐다. 정렬식이 많으면 1단계 정렬식을 원래 SELECT 식과 글자까지 맞춰야 한다. 같은 쿼리를 쓰는 화면이 많으면 효과보다 위험이 클 수 있다.

### 정렬 둘째 열에 인덱스를 못 쓸 때: 첫째 열 경계로 범위 좁히기
- 정렬이 `ORDER BY group_no DESC, path_text`처럼 둘째 열이 TEXT·CLOB이라 인덱스 정렬이 안 되면, 한 쪽(20행)을 보여 줄 때도 전체 행을 정렬한다.
- 첫째 열(group_no)은 인덱스로 셀 수 있으므로 세 값을 먼저 구한다: 이번 쪽 첫 행의 group_no(hi), 끝 행의 group_no(lo), `group_no > hi`인 행 수(above). 본 쿼리는 `lo ≤ group_no ≤ hi`인 행만 원래 정렬로 정렬하고, 건너뛸 행 수는 `(startRow-1) - above`로 줄인다.
- 같은 group_no 묶음(예: 원글과 답글)은 통째로 범위 안에 들어오므로 쪽 경계에서 갈라지지 않고 결과가 원래와 같다. 묶음 하나가 아주 크면 그 묶음이 걸친 쪽만 느려진다.
- 경계 조회가 인덱스만 읽고 끝나게, 목록 WHERE에 쓰는 기간 열까지 인덱스에 넣는다(예: `(tenant_id, board_id, group_no, start_date, end_date)`).
- 경계 조회 사이에 행이 추가되면(READ COMMITTED) above가 startRow보다 커져 음수 offset이 될 수 있다. 이때는 경계 없이 원래 쿼리로 돌아간다.
- 사용자가 다른 열로 정렬을 바꾸면 적용하지 않고 원래 쿼리를 쓴다.

### 뒤쪽 쪽은 정렬을 뒤집어 읽기
- `LIMIT offset, n`은 건너뛸 행을 다 읽는다. 끝 쪽은 반대 방향으로 정렬해 앞에서 `n`행을 읽고 애플리케이션에서 순서만 되돌리면 된다(끝 쪽 1.7초 → 0.014초 사례). 가운데 쪽은 어느 방향이든 절반을 건너뛰므로 줄지 않는다.
- 읽을 위치를 전체 건수로 계산하므로 **건수 쿼리와 목록 쿼리의 조건이 완전히 같아야** 한다(`<`와 `<=` 같은 미세한 차이도 쪽을 밀리게 한다).
- 정렬 값이 같은 행끼리 순서가 정해져 있지 않으면 뒤집은 결과가 정방향과 달라진다. 정렬 끝에 유일 키(`, id`)를 붙인다.
- 2쪽부터 옵티마이저가 "건너뛸 행이 많다"고 보고 인덱스를 버리고 전체 정렬로 바꾸는 경우가 있다(1쪽만 빠른 이유). 이때는 (정렬 열, id) 인덱스와 "이번 쪽 id만 먼저 고르고 상세는 나중에 붙이기"(지연 조인)가 도움이 된다.

### 넓은 GROUP BY와 행별 판정 건수
- 첨부 같은 1:N을 붙이려고 본문까지 30개 열로 GROUP BY하면 전체 행이 임시 테이블로 간다. 집계를 상관 서브쿼리(`(SELECT ... FROM files f WHERE f.item_id = a.id LIMIT 1)`)로 바꾸면 GROUP BY가 사라지고 정렬 인덱스를 탈 수 있다.
- "이력이 없거나 최신 판인 글만" 같은 조건을 행마다 확인하는 건수는, **전체 건수 − 제외 대상 건수** 두 번 세기로 바꾸면 빠르다(1.1초 → 0.08초 사례). 제외 대상 키가 겹치지 않아야 결과가 같다. 제외 대상이 0건이면 그 조인 자체를 건너뛴다.

### 측정 방법
- 실행 중인 앱 쿼리의 실제 계획은 MariaDB `SHOW EXPLAIN FOR <connection_id>`로 잡을 수 있다. CLI에서 잰 값이 앱과 다르면 연결 콜레이션 차이를 의심한다([MySQL 조인 컬럼 문자셋 불일치로 인덱스를 못 쓰는 문제](MySQL 조인 컬럼 문자셋 불일치로 인덱스를 못 쓰는 문제.md)).
- 로컬처럼 데이터가 적으면 요청당 고정 비용(사전 조회, 네트워크 왕복)이 대부분이라 쿼리 개선이 안 보인다. 데이터가 많은 DB에서 수정 전·후 SQL을 같은 조건으로 3회씩 번갈아 실행한다.
- 결과 동일성은 건수와 "1쪽 키를 이어 붙인 문자열의 MD5"로 비교하면 행 내용을 출력하지 않고 확인할 수 있다.
- 쿼리 캐시가 있는 버전은 `SQL_NO_CACHE`를 붙인다.

## 핵심 코드
### 1) 수정 전후 결과 동일성 (행을 출력하지 않음)
```sql
-- 1쪽 10건의 키를 이어 해시로 비교 (MySQL/MariaDB)
SELECT COUNT(*) AS cnt, MD5(GROUP_CONCAT(id ORDER BY rn)) AS page_hash
FROM (
  SELECT id, ROW_NUMBER() OVER () AS rn
  FROM ( /* 수정 전(또는 후) 목록 쿼리, LIMIT 0, 10 */ ) q
) t;
```

### 2) 실행 계획에서 읽은 행과 남긴 비율
```sql
ANALYZE FORMAT=JSON                 -- MariaDB. MySQL 8은 EXPLAIN ANALYZE
SELECT SQL_NO_CACHE ... FROM orders o JOIN order_items i ON ... WHERE ...;
-- r_rows(실제 읽은 행), r_filtered(남긴 비율), using_temporary / filesort 확인
```

### 3) 조인 순서 강제 실험 (측정용)
```sql
SELECT STRAIGHT_JOIN o.id, ...
  FROM (SELECT folder_id FROM folders WHERE owner_dept = ?) f   -- 조건이 걸리는 작은 쪽부터
  JOIN files fi ON fi.folder_id = f.folder_id
  JOIN orders o ON o.file_id = fi.id
  LEFT JOIN users u ON ...;
```

### 4) 첫째 정렬 열 경계로 범위 좁히기 (MySQL/MariaDB)
```sql
-- 인덱스: (board_id, group_no, start_date, end_date)
-- hi = startRow 번째 행의 group_no, lo = endRow 번째 행의 group_no
SELECT group_no FROM posts
 WHERE board_id = ? AND start_date <= NOW() AND end_date > NOW()
 ORDER BY group_no DESC LIMIT ?, 1;              -- offset = startRow-1 (lo는 endRow-1)

SELECT COUNT(*) FROM posts                        -- above
 WHERE board_id = ? AND start_date <= NOW() AND end_date > NOW() AND group_no > ?;   -- hi

SELECT ... FROM posts p LEFT JOIN ...             -- 원래 목록 쿼리 + 범위 조건 한 줄
 WHERE p.board_id = ? AND ... AND p.group_no BETWEEN ? AND ?                          -- lo, hi
 ORDER BY p.group_no DESC, p.path_text
 LIMIT ?, ?;                                      -- (startRow-1-above), pageSize
```

### 5) 뒤쪽 쪽 역순 읽기 (Java)
```java
int total = dao.count(cond);                      // 목록과 같은 조건이어야 함
int start = (page - 1) * size;                    // 0부터
boolean reverse = start * 2 > total;
if (reverse) {
    int fromEnd = Math.max(0, total - start - size);
    int n = Math.min(size, total - start);
    cond.put("orderDir", "ASC");                  // 정렬 방향만 반대로 (끝에 id 포함)
    cond.put("offset", fromEnd);
    cond.put("limit", n);
}
List<Item> rows = dao.list(cond);
if (reverse) Collections.reverse(rows);            // 화면 순서로 되돌림
```

### 6) DDL과 실제 DB 인덱스 대조
```sql
SELECT TABLE_NAME, INDEX_NAME, GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX) AS cols
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME IN ('orders','files','folders')
GROUP BY TABLE_NAME, INDEX_NAME;
CREATE INDEX IF NOT EXISTS idx_folders_owner_dept ON folders (owner_dept);   -- MariaDB 문법
ANALYZE TABLE folders;
```

## 주의할 점
- 카운트를 분리하면 응답 순서가 바뀐다. 화면 코드가 "건수 응답이 먼저 온다"는 우연에 기대고 있었는지 함께 본다([목록과 건수를 따로 요청할 때 응답 순서 버그](../기타/목록과 건수를 따로 요청할 때 응답 순서 버그.md)).
- 개발 DB는 자식 행 수(결재선 길이 등)가 운영보다 짧은 시험 데이터가 많아 개선 폭이 작게 나온다.
- 공용 개발 DB에 인덱스를 추가하면 다른 화면의 실행 계획도 바뀐다. 다른 사람의 측정에 영향을 줄 수 있다.
