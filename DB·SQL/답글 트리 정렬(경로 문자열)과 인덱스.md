# 답글 트리 정렬(경로 문자열)과 인덱스

> 분류: DB·SQL · 최근 갱신: 2026-11-09

## 한 줄 요약
게시판 답글을 원글 밑에 트리 순서로 보이려고 "부모 경로 + 역순 시각 + 글 ID" 같은 경로 문자열로 정렬하면 답글 저장은 단순하지만, 열이 TEXT·CLOB이면 인덱스 정렬이 안 돼 목록마다 전체를 정렬한다. 근본 해결은 인덱스 가능한 정렬 열이고, 요즘은 원글 단위로 쪽을 나누는 설계를 많이 쓴다.

## 내용
### 경로 문자열로 트리 순서가 나오는 원리
- 정렬은 `ORDER BY thread_no DESC, path ASC` 두 단계다. `thread_no`(원글 번호)는 원글과 그 답글이 같은 값을 가져 글타래를 최신순으로 묶고, `path`가 글타래 안 순서를 정한다.
- 원글의 path = 자기 ID, 답글의 path = 부모 path + 역순 시각(예: `9999-년`, `12-월`처럼 늦을수록 작아지는 고정 길이 숫자) + 자기 ID.
- 오름차순으로 정렬하면 (1) 원글이 맨 위(모든 답글 값의 앞부분) (2) 자식이 부모 바로 밑(깊이 우선) (3) 같은 단계는 최근 답글이 위(역순 시각)가 된다.
- 순번 방식(목록 순서를 정수로 저장)은 정렬이 빠르지만 중간에 답글이 끼면 뒤 글을 모두 UPDATE해야 한다. 경로 방식은 답글을 달 때 다른 행을 건드리지 않는다. 대신 깊이마다 값이 길어진다(예: 단계마다 14+38 = 52자).

### 인덱스가 안 되는 이유와 영향
- MySQL `LONGTEXT`·Oracle `NCLOB`은 정렬용 인덱스에 넣을 수 없다. 첫 쪽 20행을 보여 줄 때도 게시판 전체 행을 읽어 정렬한다(10만 행 7~8초 사례).
- 테이블을 바꾸지 않는 우회: 첫째 열(thread_no) 경계로 범위를 좁혀 그 범위만 정렬([페이징 목록 쿼리가 느린 원인과 개선 측정](페이징 목록 쿼리가 느린 원인과 개선 측정.md)).

### 열 형식을 VARCHAR로 바꿀 때 계산할 것
- 최대 길이 = 원글 길이 + 단계당 길이 × 허용 깊이. 실제 데이터의 `MAX(LENGTH(path))`와 깊이 분포를 먼저 본다(보통 2~5단계).
- MySQL InnoDB 인덱스 키는 3,072바이트까지다. utf8mb4는 글자당 4바이트로 계산되므로 값이 ASCII뿐이면 열 문자셋을 ascii로 두면 여유가 생긴다. 한도를 넘는 답글은 저장할 때 막는다.
- MySQL `ALTER ... MODIFY`는 표를 다시 쓴다(시간·잠금). Oracle은 CLOB→VARCHAR2 직접 변경이 안 돼 새 열 추가 → 복사 → 삭제 → 이름 변경 순서로 한다. 매퍼에 `TO_CHAR(path)` 같은 함수 정렬이나 CLOB 타입 매핑이 남아 있으면 인덱스를 못 탄다.
- **정렬 방향이 섞이면**(`DESC, ASC`) 내림차순 인덱스가 필요하다. MySQL 8·Oracle은 되지만 MariaDB는 10.8부터라, 그 아래 버전은 형식을 바꿔도 전체 정렬이 남는다.
- 형식만 바꿔도 목록 쿼리에 넓은 GROUP BY가 있으면 인덱스 순서로 읽지 못한다. GROUP BY 제거와 함께 해야 효과가 난다.

### 정렬용 열을 새로 둘 때
- DDL, 기존 행 값 채우기, 글 작성·답글·이동·복사·삭제·이력 등 순서를 바꾸는 모든 쓰기 경로를 함께 고쳐야 한다. 하나라도 빠지면 목록 순서가 틀어진다.
- 여러 사이트가 소스 하나를 쓰면 "신규 사이트만"이 오히려 어렵다(코드가 두 갈래). 설정값으로 나눌 때는 **열은 모든 곳에 추가하고 쓰기는 항상 채우되, 설정으로는 읽기(정렬)만** 나누는 편이 관리하기 쉽다. 순서는 DDL → 값 채우기 → 설정 켜기, 켠 뒤 끄면 그 사이 글이 비어 다시 켤 때 채우기가 또 필요하다.

### 요즘 설계
1. 답글 대신 댓글 테이블을 두고 목록은 원글만 정렬(인덱스 하나로 끝).
2. `parent_id`·`root_id`를 저장하고 **원글 단위로 쪽을 나눈 뒤** 그 원글들의 답글만 `root_id IN (...)`으로 가져와 재귀 쿼리(`WITH RECURSIVE`, Oracle `CONNECT BY`)나 앱에서 트리 순서로 맞춘다.
3. 경로 방식을 유지하되 인덱스 가능한 고정 길이 VARCHAR(PostgreSQL은 `ltree` 타입).
- 정확한 전체 건수 대신 "더보기"·무한 스크롤, 쪽 번호 대신 keyset 페이징을 함께 쓰는 경우가 많다.

## 핵심 코드
### 1) 경로 값 만들기 (Java)
```java
// 늦게 쓸수록 작은 값이 되는 고정 길이 시각 (24시간제 사용)
static String reverseTimestamp(LocalDateTime t) {
    return String.format("%04d%02d%02d%02d%02d%02d",
        9999 - t.getYear(), 12 - t.getMonthValue(), 31 - t.getDayOfMonth(),
        23 - t.getHour(), 59 - t.getMinute(), 59 - t.getSecond());
}
String path = (parent == null) ? postId : parent.getPath() + reverseTimestamp(now) + postId;
```

### 2) 변환 전 점검과 열 변경 (MySQL)
```sql
SELECT MAX(LENGTH(path)) AS max_len,
       MAX((LENGTH(path) - 38) DIV 52) AS max_depth      -- 원글 38자, 단계당 52자인 경우
  FROM posts;

ALTER TABLE posts MODIFY path VARCHAR(500) CHARACTER SET ascii COLLATE ascii_bin NOT NULL;
CREATE INDEX idx_posts_list ON posts (board_id, thread_no DESC, path);   -- MySQL 8 / MariaDB 10.8+
```

### 3) 원글 단위 쪽 나누기 (MySQL 8 / MariaDB 10.2+)
```sql
-- 1) 이번 쪽 원글 20개
SELECT id FROM posts WHERE board_id = ? AND parent_id IS NULL
 ORDER BY created_at DESC, id DESC LIMIT ?, 20;
-- 2) 그 원글들의 글타래 전체를 트리 순서로
WITH RECURSIVE t AS (
  SELECT id, parent_id, root_id, title, CAST(LPAD(id, 12, '0') AS CHAR(600)) AS sort_key
    FROM posts WHERE id IN (/* 1)의 id */)
  UNION ALL
  SELECT c.id, c.parent_id, c.root_id, c.title, CONCAT(t.sort_key, LPAD(c.id, 12, '0'))
    FROM posts c JOIN t ON c.parent_id = t.id
)
SELECT * FROM t ORDER BY root_id DESC, sort_key;
```

## 주의할 점
- 시각을 12시간제(`hh`)로 만들면 오전·오후가 같은 값이 되어 순서가 섞인다. 24시간제로 만든다.
- 원글 단위 쪽 나누기는 쪽마다 줄 수가 달라지고, 건수·쪽 수 표시의 뜻이 바뀐다. 원글이 목록에 안 보이는 답글(원글 만료·권한 없음·안 읽은 글 보기)을 어떻게 셀지 정해야 한다. 사양 변경이므로 성능 목적만으로 바꾸지 않는다.
- 사용자가 제목·작성자로 정렬을 바꾸면 트리 정렬이 아니므로 별도 경로로 둔다.
