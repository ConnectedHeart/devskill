# WAF 웹 애플리케이션 방화벽과 오탐 대응

> 분류: 네트워크 · 최근 갱신: 2026-10-15

## 한 줄 요약
WAF는 HTTP 요청 내용(L7)을 보고 웹 공격 패턴을 막는 장비·모듈이며, 정상 입력을 공격으로 오탐해 403을 내는 경우가 많아 "저장이 안 된다"는 문의에서 서버 로그에 요청이 없으면 먼저 의심한다.

## 내용
### 일반 방화벽과의 차이
- 일반 방화벽은 IP·포트(L3/L4) 단위로 허용·차단한다. WAF는 HTTP/HTTPS 요청의 URL, 파라미터, 본문, 헤더를 들여다본다.
- 주로 막는 것: SQL Injection(`' OR 1=1 --`), XSS(`<script>` 태그), 경로 조작(`../../etc/passwd`), 악성 업로드 패턴, 과도한 요청(Rate limiting).

### 동작 방식
- 클라이언트와 웹서버 사이에 둔다. 리버스 프록시 형태의 어플라이언스이거나, Apache/Nginx 모듈(ModSecurity)로 붙는다. 클라우드는 AWS WAF, Cloudflare WAF 등이다.
- 시그니처(룰셋) 기반으로 요청을 검사해 차단하거나 로그만 남긴다(탐지 모드).

### 실무에서 겪는 일
- 게시글 본문이나 파일명에 `<script>`, `select ... from`, `../` 같은 문구가 들어가면 정상 요청인데도 403이 떨어진다.
- 증상: 특정 화면에서만 저장이 안 되고, 애플리케이션 서버 로그에는 그 요청이 아예 찍히지 않는다. 요청이 서버에 닿기 전에 막힌 것이다.
- 대응: WAF 쪽에서 해당 URL·파라미터를 예외 등록하거나, 애플리케이션에서 입력값을 인코딩(Base64, URL 인코딩)해 보내고 서버에서 푼다. 에디터 본문처럼 HTML이 정상인 입력은 예외 등록이 현실적이다.

## 예시
```
# 403이 WAF 차단인지 가르는 순서
1. 애플리케이션 서버 access 로그에 요청이 있는가 → 없으면 앞단 차단
2. 같은 요청에서 특수 문구만 빼고 보내면 성공하는가 → 룰 오탐
3. 고객사 네트워크 담당에게 WAF 차단 로그 확인 요청 (시각, URL, 룰 ID)
```

## 주의할 점
- 403 응답 본문이 애플리케이션이 아닌 장비 페이지(짧은 HTML, 장비 이름)라면 WAF일 가능성이 크다.
- 예외 등록은 그 URL의 방어를 푸는 것이므로 범위를 파라미터 단위로 최소화한다.
