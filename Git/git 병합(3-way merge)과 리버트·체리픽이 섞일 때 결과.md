# git 병합(3-way merge)과 리버트·체리픽이 섞일 때 결과

> 분류: Git · 최근 갱신: 2026-11-05

## 한 줄 요약
git 병합은 커밋을 하나씩 다시 실행하지 않고 공통 조상(merge base)·내 브랜치 끝·상대 브랜치 끝 세 상태만 비교한다. 그래서 상대 브랜치에서 "넣었다가 뺀" 변경은 병합에 아무 영향이 없고, 리버트가 다른 브랜치로 넘어가는지는 리버트 시점에 공통 조상이 어디였는지로 정해진다.

## 내용
### 줄마다 정하는 규칙
| 공통 조상 | 내 끝 | 상대 끝 | 병합 결과 | 이유 |
|---|---|---|---|---|
| 없음 | 있음 | 없음 | 있음 | 나만 바뀜(추가) |
| 있음 | 있음 | 없음 | 없음 | 상대만 바뀜(삭제가 적용됨) |
| 있음 | 없음 | 있음 | 없음 | 나만 바뀜(삭제) |
| 없음 | 있음 | 있음 | 있음 | 양쪽이 같게 추가 |
| 있음 | 수정 A | 수정 B | 충돌 | 양쪽이 다르게 바뀜 |

- 커밋별 우선순위는 없다. "추가 커밋 + 삭제 커밋"이 한 브랜치에 있으면 끝 상태가 공통 조상과 같아져 그 브랜치는 그 줄에 대해 "한 일이 없는" 것으로 본다. 삭제가 무시된 것이 아니라 상쇄된 것이다.
- 병합 결과 이력(`git log`)에는 그 커밋들이 보이지만, 파일 내용에는 적용되지 않을 수 있다.

### 체리픽 후 리버트가 다른 브랜치로 넘어가는지
1. **체리픽으로 넣고, 병합하기 전에 리버트** → 상대 브랜치의 원래 기능은 유지된다. 공통 조상 이후 상대 쪽 순변화가 0이기 때문이다.
   ```
   dev   : A ── X(기능) ─────────────────── M
   main  : A ── X'(체리픽) ── R(X' 리버트) ┘
   ```
2. **한 번 병합해 공통 조상이 X' 뒤로 옮겨진 다음 리버트** → 다음 병합에서 상대 브랜치에서도 기능이 빠진다. 공통 조상 이후 변화가 R(삭제)뿐이기 때문이다. 브랜치를 체리픽이 아닌 병합으로 받아 X 자체가 들어간 경우도 같다.
   ```
   dev   : A ── X ── M1 ──────────── M2
   main  : A ── X' ─┘ ── R(리버트) ─┘
   ```
- 그래서 "main에서만 빼고 dev에는 남겨야" 하는 변경은, 병합할 때 그 부분을 dev 쪽으로 되살리거나 병합 뒤 dev에서 리버트를 다시 되돌려야 한다.

### 미반영 커밋을 골라 옮길 때
- 원본 브랜치에서 이미 리버트된 커밋을 다른 브랜치에 체리픽하면, 나중에 역병합할 때 원본 브랜치에 그 기능이 되살아날 수 있다. 커밋을 고를 때 원본 브랜치의 `Revert "..."` 커밋도 함께 확인한다.
- 실수로 넣었다면 병합 전에 대상 브랜치에서 리버트해 두면 1번 경우가 되어 원본에는 영향이 없다.

### 한 브랜치를 두 작업트리에서 쓸 수 없음
- `git checkout <브랜치>`가 `'<브랜치>' is already used by worktree at ...`로 실패하면 그 브랜치가 다른 작업트리에 체크아웃된 상태다. 그 작업트리에 변경이 없는지 확인한 뒤 `git worktree remove`로 지우면 된다. 브랜치와 커밋은 그대로 남는다.

## 핵심 코드
```bash
# 병합 기준점과 세 상태에서 특정 줄 확인
base=$(git merge-base dev main)
for rev in $base dev main; do
  echo "== $rev"; git show "$rev:path/to/file.sql" | grep -n "some-menu-row" || echo "(없음)"
done
```

```bash
# 원본 브랜치에서 리버트된 커밋인지 확인 (제목으로)
git log dev --oneline --grep='^Revert "' | grep -F "<커밋 제목 일부>"
# 해시로 찾기: 리버트 커밋 본문에 "This reverts commit <hash>"가 남는다
git log dev --oneline --grep="This reverts commit <hash>"
```

```bash
# 병합 결과를 미리 보기 (작업트리를 건드리지 않음, git 2.38+)
git merge-tree --write-tree dev main
```

```bash
# 다른 작업트리에 잡혀 있는 브랜치 풀기
git worktree list
git -C <작업트리 경로> status --short      # 변경이 없는지 확인
git worktree remove <작업트리 경로>
```

## 주의할 점
- 병합 결과를 이해할 때 "어떤 커밋이 들어왔나"보다 "공통 조상 대비 각 끝 상태가 어떻게 달라졌나"를 본다.
- 공통 조상은 병합할 때마다 옮겨진다. push된 병합 이후의 리버트는 반대 브랜치에도 퍼진다고 생각하고 계획한다.
