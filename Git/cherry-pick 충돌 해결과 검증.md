# cherry-pick 충돌 해결과 검증

> 분류: Git · 최근 갱신: 2026-10-21

## 한 줄 요약
여러 커밋을 다른 브랜치로 체리픽할 때는 순서와 선행 커밋이 중요하고, 끝난 뒤에는 원 커밋의 변경분과 파일 단위로 대조해야 누락을 잡을 수 있다.

## 내용
### 순서와 선행 커밋
- 체리픽은 커밋의 변경분만 옮긴다. 그 커밋이 의존하는 앞선 커밋(새 클래스, 메서드 시그니처 변경 등)이 대상 브랜치에 없으면 충돌 없이 반영되고도 컴파일이 깨진다.
- 앞 커밋이 빠지면 뒤 커밋들이 연쇄로 충돌한다. 시간순으로 반영하고, 컴파일 오류가 나면 빠진 선행 커밋부터 찾는다.

### 일부만 골라 담는 브랜치에서 충돌이 많은 이유
개발 브랜치의 커밋은 앞 커밋 위에 쌓여 있는데, 골라 담는 브랜치에는 그 "앞 커밋"이 없을 수 있다. 충돌은 대체로 세 가지 형태다.
1. **앞 커밋이 만든 줄을 뒤 커밋이 고치는 경우** — 대상 브랜치에는 고칠 줄 자체가 없다. 여러 파일의 호출부를 한꺼번에 바꾸는 커밋(함수 이름·위치 변경 등)은 파일마다 한 줄만 건드려도 파일 수만큼 앞 커밋에 묶인다.
2. **여러 사람이 같은 자리에 덧붙이는 공용 파일** — 다국어 메시지, 설정 파일처럼 파일 끝에 키를 추가하는 파일은 내용이 무관해도 같은 위치라 충돌한다. 양쪽 줄을 모두 살리면 된다.
3. **나중 수정이 먼저 들어가 있는 경우** — 대상 브랜치에 최근 수정이 먼저 반영돼 있으면, 예전 커밋을 뒤늦게 넣을 때 같은 줄을 양쪽이 다르게 바꾼 것으로 보인다. 이때는 대상 브랜치의 값이 최신이고 커밋 안의 값이 옛 값일 수 있으므로, 원본 브랜치의 최신 코드와 비교해 어느 쪽이 최종인지 판단한다.

오래된 커밋일수록 그 위에 쌓인 것이 많아 선행 조건이 늘어난다. 최근 커밋이고 다른 작업과 파일이 겹치지 않는 영역은 깨끗하게 들어간다.

### 선행 커밋 찾는 방법
- 충돌한 파일에서 "이 커밋이 고치려는 줄을 처음 넣은 커밋"을 찾는다(`git log -S`, `git blame <커밋>^ -- <파일>`). 그 커밋이 대상 브랜치에 없으면 선행 커밋이다. 찾은 커밋에 대해 같은 추적을 반복한다.
- 줄 단위 추적은 "다른 파일의 함수나 CSS에 기대는" 의존은 잡지 못한다. 충돌 없이 들어갔더라도, 새로 호출하는 함수의 정의가 대상 브랜치에 있는지 따로 검색해야 한다. 실제로 호출만 따라 들어오고 정의가 없어 화면 스크립트 오류가 나는 경우가 있다.
- 선행 커밋 전체를 넣기 부담스러우면 "겹치는 파일만 손으로 맞추기"도 선택지다. 다만 그 기능의 일부만 들어가지 않게, 대상 브랜치에 없는 기능의 코드는 충돌 블록에서 빼야 한다.
- **충돌을 손으로 풀기 전에 두 경우를 가른다.**
  - *선행 커밋이 필요한 경우*: 이 커밋이 고치는 줄(예: 툴바의 특정 자리 요소)을 앞 커밋이 만들었는데 대상 브랜치에 없다. 이때 "이 커밋의 줄만 넣기"로 풀면 원 커밋과 다른 내용이 들어가고 뒤 커밋도 연쇄로 어긋난다. 멈추고 선행 커밋(해시·작성자·일시·제목·필요한 이유)을 정리해 결정을 받은 뒤, 선행 커밋을 시간순 위치에 넣으면 원 커밋이 충돌 없이 그대로 들어간다.
  - *옆줄이 겹치기만 한 경우*: 대상 브랜치에 없는 **다른 기능**의 줄이 바로 옆에 있어 문맥만 겹친다. 이 커밋이 추가하는 줄이 그 기능을 쓰지 않으면 선행 커밋은 필요 없고, 이 커밋의 줄만 넣는 것이 맞다.
  - 팀 규칙으로 "충돌은 임의로 고치지 않고, `git log -S`로 원인 커밋을 찾아 보고한다"를 정해 두면 판단이 사람마다 달라지지 않는다.
- 이미 임의로 풀어 쌓았다면, 백업 브랜치를 남기고 대상 브랜치를 원격 상태로 되돌린 뒤 선행 커밋을 포함해 처음부터 다시 쌓는 편이 깔끔하다.
- 연속 작업(같은 제목에 번호가 붙은 커밋들)에서 중간 커밋이 넣은 형태를 뒤 커밋이 다시 고친다면, 충돌을 풀 때 **중간 커밋의 형태를 그대로 맞춰 둬야** 뒤 커밋이 충돌 없이 이어진다.

### 임시 worktree에서 먼저 시험
- `git worktree add`로 임시 폴더를 만들어 시험 체리픽을 해 보면 어느 커밋이 충돌하는지 본 작업 폴더를 건드리지 않고 알 수 있다.
- 같은 브랜치를 두 worktree에서 동시에 체크아웃할 수 없다. 시험이 끝나면 worktree를 제거해야 원래 폴더에서 그 브랜치로 전환할 수 있다.
- `git cherry-pick -n`(커밋 없이 적용)으로 여러 건을 이어 적용해 보고 되돌리는 방식으로도 "이 순서면 충돌이 없는지"를 확인할 수 있다.

### 충돌 해결 중 상태 보존
- 체리픽 진행 중에는 브랜치를 전환할 수 없다. 해결해 둔 상태를 남기고 다른 커밋부터 처리하려면 `git cherry-pick --quit`으로 진행 상태만 끝낸 뒤(작업 트리는 유지) 백업 브랜치에 커밋한다.
- 충돌 표시를 공통 조상(base)까지 보이는 형식으로 만들면 "양쪽이 각각 무엇을 바꿨는지"를 판단하기 쉽다.

### 반영 후 중간 커밋에 변경 합치기
- 체리픽을 끝낸 뒤 "이 설정 값은 그 키를 추가한 원래 커밋에 들어가야 한다"처럼 중간 커밋을 고쳐야 하면 fixup + autosquash 리베이스로 합친다. 고친 커밋부터 끝까지 해시가 전부 바뀌므로 푸시 전에만 한다.
- 합치기 전 끝 커밋과 합친 뒤 끝 커밋을 `git diff`로 비교해, 의도한 변경 외에 차이가 없는지 확인한다.

### 결과 검증 순서
1. 원 커밋과 결과 커밋의 변경 파일 목록 비교
2. 파일별로 "대상 브랜치 대비 현재 변경분"과 "원 커밋 변경분"을 1:1 대조 — 추가 줄 누락, 삭제되지 않은 줄, 대상 브랜치에 원래 있던 줄의 유실
3. 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`) 전체 검색
4. 컴파일, JS 문법 검사(`node --check`)
5. 새 코드가 참조하는 것들이 대상 브랜치에 있는지 검색 — 함수 정의, 메시지 키, SQL ID, 요청 주소, 정적 파일
6. 새 SQL이 쓰는 테이블·컬럼이 대상 브랜치의 DDL에 있는지, 새로 읽는 설정 키가 있는지, 이름으로 주입하는 빈이 있는지
7. 서버와 클라이언트가 두 저장소로 나뉜 기능이면 짝 커밋이 양쪽 대상 브랜치에 모두 들어갔는지(한쪽만 들어가면 메뉴는 보이는데 화면이 없는 식의 반쪽 기능이 된다)

## 예시
```bash
git show <커밋> -- <경로>                     # 그 커밋이 그 파일에서 바꾼 내용
git show <커밋> -- '*파일명'                  # 경로 대신 패턴
git show --numstat --format= <커밋> -- <파일>  # 추가/삭제 줄 수만
git show <커밋>:<경로>                        # 그 커밋 시점의 파일 전체

git config merge.conflictStyle diff3          # 충돌 표시에 base 포함
git worktree add ../trial <브랜치>            # 시험용 worktree
git worktree remove ../trial

git log -S'functionName(' --oneline <원본 브랜치> -- <경로>   # 그 문자열을 넣거나 뺀 커밋
git log --oneline --no-merges <대상>..<원본>                  # 원본에만 있는 커밋
git log --format=%s <대상> | sort -u                           # 대상 브랜치의 커밋 제목 목록(제목 비교용)
```

## 주의할 점
- 충돌 표시 검색은 소스뿐 아니라 SQL, properties 같은 텍스트 파일 전체를 대상으로 한다. 컴파일 대상이 아닌 파일에 남은 표시는 빌드에서 걸리지 않는다.
- 줄 끝이 CRLF인 파일은 도구가 구분선을 잘못 인식할 수 있으므로 해결 결과를 다시 확인한다.
- 유니코드 이스케이프(`\uXXXX`)의 대소문자만 다른 properties 파일은 줄 단위 비교가 전부 다르게 나온다. 키 단위로 비교한다.
- diff 문맥에 걸려 보이는 줄과 실제로 바뀐 줄을 구분한다.
- 원 커밋 자체가 실수로 줄을 지운 경우도 있다. 대상 브랜치에 값이 남은 것이 오히려 정상일 수 있다.
- 내용이 같은데도 충돌하는 경우가 있다. 빈 줄처럼 보이는 줄에 한쪽만 탭·공백이 들어 있으면 문맥이 달라 자동 병합이 안 된다. 공백까지 보이게 해서 비교한다(`git diff --ws-error-highlight=all`, `cat -A`).
- 체리픽으로 옮긴 커밋은 메시지와 Author는 유지되지만 커밋 일시(committer date)는 옮긴 날로 바뀐다.
- "원본 브랜치에만 있는 커밋"을 제목으로 비교하면, 제목을 바꿔 넣었거나 여러 커밋을 합쳐 넣은 경우가 미반영으로 잡힌다. Revert와 그 원 커밋의 짝도 따로 걸러야 한다. `git cherry`나 `git log --cherry-pick`은 변경 내용(patch-id) 기준이라 충돌을 풀며 넣은 커밋은 다른 것으로 본다.
- 설정 파일을 체리픽할 때는 원본 커밋에 개발 환경 값(서버 주소 등)이 섞여 있는지 본다. 새 키만 받고 기존 키의 값은 대상 브랜치 것을 유지하는 식으로 나눠 판단한다.
- 정적 검사를 모두 통과해도 화면 동작이 확인된 것은 아니다. JSP처럼 처음 요청될 때 컴파일되는 파일의 오류는 빌드에서 잡히지 않는다.
