# cherry-pick 충돌 해결과 검증

> 분류: Git · 최근 갱신: 2026-09-30

## 한 줄 요약
여러 커밋을 다른 브랜치로 체리픽할 때는 순서와 선행 커밋이 중요하고, 끝난 뒤에는 원 커밋의 변경분과 파일 단위로 대조해야 누락을 잡을 수 있다.

## 내용
### 순서와 선행 커밋
- 체리픽은 커밋의 변경분만 옮긴다. 그 커밋이 의존하는 앞선 커밋(새 클래스, 메서드 시그니처 변경 등)이 대상 브랜치에 없으면 충돌 없이 반영되고도 컴파일이 깨진다.
- 앞 커밋이 빠지면 뒤 커밋들이 연쇄로 충돌한다. 시간순으로 반영하고, 컴파일 오류가 나면 빠진 선행 커밋부터 찾는다.

### 임시 worktree에서 먼저 시험
- `git worktree add`로 임시 폴더를 만들어 시험 체리픽을 해 보면 어느 커밋이 충돌하는지 본 작업 폴더를 건드리지 않고 알 수 있다.
- 같은 브랜치를 두 worktree에서 동시에 체크아웃할 수 없다. 시험이 끝나면 worktree를 제거해야 원래 폴더에서 그 브랜치로 전환할 수 있다.

### 충돌 해결 중 상태 보존
- 체리픽 진행 중에는 브랜치를 전환할 수 없다. 해결해 둔 상태를 남기고 다른 커밋부터 처리하려면 `git cherry-pick --quit`으로 진행 상태만 끝낸 뒤(작업 트리는 유지) 백업 브랜치에 커밋한다.
- 충돌 표시를 공통 조상(base)까지 보이는 형식으로 만들면 "양쪽이 각각 무엇을 바꿨는지"를 판단하기 쉽다.

### 결과 검증 순서
1. 원 커밋과 결과 커밋의 변경 파일 목록 비교
2. 파일별로 "대상 브랜치 대비 현재 변경분"과 "원 커밋 변경분"을 1:1 대조 — 추가 줄 누락, 삭제되지 않은 줄, 대상 브랜치에 원래 있던 줄의 유실
3. 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`) 전체 검색
4. 컴파일, JS 문법 검사(`node --check`)

## 예시
```bash
git show <커밋> -- <경로>                     # 그 커밋이 그 파일에서 바꾼 내용
git show <커밋> -- '*파일명'                  # 경로 대신 패턴
git show --numstat --format= <커밋> -- <파일>  # 추가/삭제 줄 수만
git show <커밋>:<경로>                        # 그 커밋 시점의 파일 전체

git config merge.conflictStyle diff3          # 충돌 표시에 base 포함
git worktree add ../trial <브랜치>            # 시험용 worktree
git worktree remove ../trial
```

## 주의할 점
- 충돌 표시 검색은 소스뿐 아니라 SQL, properties 같은 텍스트 파일 전체를 대상으로 한다. 컴파일 대상이 아닌 파일에 남은 표시는 빌드에서 걸리지 않는다.
- 줄 끝이 CRLF인 파일은 도구가 구분선을 잘못 인식할 수 있으므로 해결 결과를 다시 확인한다.
- 유니코드 이스케이프(`\uXXXX`)의 대소문자만 다른 properties 파일은 줄 단위 비교가 전부 다르게 나온다. 키 단위로 비교한다.
- diff 문맥에 걸려 보이는 줄과 실제로 바뀐 줄을 구분한다.
- 원 커밋 자체가 실수로 줄을 지운 경우도 있다. 대상 브랜치에 값이 남은 것이 오히려 정상일 수 있다.
