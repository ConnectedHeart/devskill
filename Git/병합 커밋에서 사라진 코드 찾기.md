# 병합 커밋에서 사라진 코드 찾기

> 분류: Git · 최근 갱신: 2026-10-27

## 한 줄 요약
누군가의 병합 커밋이 충돌 해결 중에 한쪽 브랜치의 코드를 지웠는지 확인하려면, 같은 두 부모를 다시 병합해 실제 병합 커밋과 비교한다.

## 내용
**왜 일반 diff로는 안 보이나**
- 병합 커밋은 부모가 둘이라 `git show`의 기본 출력(combined diff)은 "양쪽 부모와 모두 다른" 부분만 보여 준다. 한쪽 부모의 내용을 그대로 택하면서 다른 쪽의 추가분을 버린 경우는 눈에 잘 띄지 않는다.

**재병합 비교 절차**
1. 병합 커밋의 두 부모를 확인한다 (`M^1` = 병합을 실행한 브랜치 쪽, `M^2` = 가져온 브랜치 쪽).
2. 임시 worktree에서 `M^1`을 체크아웃하고 `M^2`를 같은 방식으로 다시 병합한다.
3. 충돌 없이 병합된 파일은 재병합 결과와 실제 병합 커밋이 같아야 한다. 다르면 누군가 손으로 바꾼 것이다(evil merge).
4. 충돌이 난 파일만이 사람이 손댄 범위다. 이 파일들은 "우리 쪽 우선(`-X ours`)"과 "상대 쪽 우선(`-X theirs`)" 두 가지 자동 해결 결과와 각각 비교해, 한쪽에서만 있던 줄이 빠졌는지 본다.

**"지워졌다"의 판정 기준**
- 분기점(merge-base) 이후 한쪽 브랜치가 추가했고,
- 병합 직전 그 브랜치에는 있었는데,
- 병합 결과에는 없는 줄.
- 어느 쪽 우선으로 해결했더라도 남아 있어야 하는 줄이 빠졌다면 충돌 해결 중 실수일 가능성이 크다.

**영향 확인과 복구**
- 지워진 메서드·키를 참조하는 코드가 남아 있는지 검색한다. 컴파일이 되는 언어라도 템플릿, 스크립트, 메시지 키 참조는 컴파일로 잡히지 않는다.
- 복구는 병합 직전 부모(`M^1`)의 해당 부분을 그대로 가져와 새 커밋으로 만든다. 상대 브랜치에서 들어온 정상 변경은 건드리지 않는다.
- 다른 브랜치가 이미 깨진 병합 결과를 가져갔다면, 복구 커밋을 한 번 더 병합해 이력을 맞춘다. 그 브랜치가 해당 코드를 이미 갖고 있으면 내용 변화 없이 이력만 정리된다.

**브랜치별 컴파일 확인**
- 작업 폴더를 건드리지 않으려면 각 브랜치의 빌드에 필요한 경로만 임시 폴더로 꺼내서(`git archive` 또는 worktree) 빌드한다.

## 핵심 코드
### 1) 부모 확인과 빠른 점검
```bash
git log -1 --format='%H %P' <병합커밋>          # 병합 커밋과 두 부모
git merge-base <병합커밋>^1 <병합커밋>^2         # 분기점

# 최신 git(2.36 이상)이면 한 줄로: 자동 재병합 결과와 실제 병합의 차이만 출력
git show --remerge-diff <병합커밋>
```

### 2) 재병합해 보기 (작업 폴더와 분리)
```bash
git worktree add --detach ../remerge <병합커밋>^1
cd ../remerge
git merge --no-commit --no-ff <병합커밋>^2      # 충돌 파일 목록 = 사람이 손댄 범위
git diff --name-only --diff-filter=U            # 충돌 파일만
git diff <병합커밋> -- <충돌 없던 경로>          # 충돌 없던 파일이 실제 병합 결과와 같은지(출력이 없어야 정상)
git merge --abort
```

### 3) 충돌 파일을 양쪽 자동 해결 결과와 비교
```bash
git merge --no-commit --no-ff -X ours <병합커밋>^2      # 우리 쪽 우선
git diff <병합커밋> -- <충돌 파일>
git merge --abort
git merge --no-commit --no-ff -X theirs <병합커밋>^2    # 상대 쪽 우선
git diff <병합커밋> -- <충돌 파일>
git merge --abort
cd - && git worktree remove --force ../remerge
```

### 4) 한쪽이 추가했는데 결과에서 빠진 줄 찾기
```bash
base=$(git merge-base <병합커밋>^1 <병합커밋>^2)
git diff "$base" <병합커밋>^2 -- <파일>          # 상대 브랜치가 추가한 줄(+)
git diff <병합커밋>^2 <병합커밋> -- <파일>       # 병합 결과에서 그 줄이 빠졌으면 - 로 보인다
git log -S'<문자열>' --oneline -- <경로>         # 특정 문자열을 넣거나 뺀 커밋 찾기
git branch -a --contains <커밋>                  # 커밋이 어느 브랜치에 들어 있는지
```

### 5) 복구 커밋 만들기
```bash
git switch <브랜치>
git restore --source=<병합커밋>^1 -- <파일>      # 병합 직전 부모의 파일로 되돌림
git diff                                         # 상대 브랜치에서 들어온 정상 변경까지 지워지지 않았는지 보고 손으로 정리
git add <파일> && git commit -m "병합 중 사라진 <기능> 코드 복구"
```

### 6) 브랜치별 컴파일 확인용으로 꺼내기
```bash
mkdir -p /tmp/build-<브랜치>
git archive <브랜치> <빌드에 필요한 경로들> | tar -x -C /tmp/build-<브랜치>
```

## 주의할 점
- 자동 병합이 "성공"해도 결과가 옳다는 보장은 없다. 양쪽에 같은 코드가 이미 있으면 한 번 더 붙어 중복 정의가 되거나, 주석 경계가 어긋나 컴파일이 깨질 수 있다. 병합 후 컴파일은 따로 확인한다.
- Java 컴파일만으로는 JSP·JS·SQL 매퍼 XML(중복 id 등)과 실행 시 오류를 잡지 못한다.
- 환경별로 값이 달라야 하는 설정 파일은 병합 때 어느 쪽 값을 유지할지 의식적으로 정한다.
