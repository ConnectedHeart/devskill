# git 체리픽·병합·워크트리 문법 정리 (초보자용)

> 이 저장소에서 체리픽(develop → 릴리즈·master), 병합(릴리즈 → master → develop), 워크트리 작업을 할 때 Claude가 실제로 쓰는 명령을 모았다.
> 예시의 브랜치 이름: 개발 `develop`, 릴리즈 `release-1.0`(아래에서는 줄여 `<릴리즈>`), `master`.

---

## 0. 먼저 알아 둘 낱말 5개

| 낱말 | 뜻 | 비유 |
|---|---|---|
| **커밋(commit)** | 파일 변경을 묶어 저장한 한 단위. `a9d602e3cd` 같은 해시(고유번호)로 가리킨다 | 저장 버튼 한 번 |
| **브랜치(branch)** | 커밋 줄의 맨 끝을 가리키는 이름표 | 책갈피 |
| **HEAD** | 지금 내가 서 있는 커밋(보통 현재 브랜치의 끝) | "현재 위치" 표시 |
| **원격 추적 브랜치** | `origin/develop`처럼 서버 상태를 마지막으로 받아 온 사본. `git fetch` 때만 갱신된다 | 서버 사진 한 장 |
| **작업 폴더(working tree)** | 실제로 파일이 놓인 폴더. 한 폴더에는 한 번에 한 브랜치만 꺼내 놓을 수 있다 | 책상 |

> 핵심: **로컬 브랜치(`<릴리즈>`)와 원격 추적 브랜치(`origin/<릴리즈>`)는 다르다.** 로컬이 서버보다 수십 커밋 뒤처진 상태로 비교하면 엉뚱한 결과가 나온다. 그래서 언제나 fetch부터 한다.

## 1. 커밋을 가리키는 문법

| 문법 | 뜻 | 예 |
|---|---|---|
| `abc1234` | 해시 앞부분(7~10자면 충분) | `git show 2254e2d6f5` |
| `HEAD` | 지금 위치 | `git log HEAD` |
| `커밋~1` | 한 칸 앞(부모) 커밋. `~2`는 두 칸 앞 | `git diff abc1234~1 abc1234` |
| `커밋^` | 첫 번째 부모. 병합 커밋이면 `^2`가 두 번째 부모 | `git show 머지커밋^2` |
| `A..B` | **B에는 있고 A에는 없는** 커밋 | `git log <릴리즈>..develop` = 릴리즈에 아직 없는 develop 커밋 |
| `A...B` | 둘 중 한쪽에만 있는 커밋(양쪽 차이) | `git log --left-right <릴리즈>...develop` |

> 주의: Windows cmd를 거치는 실행(node `execSync` 등)에서는 `^`가 사라진다. **`커밋^` 대신 `커밋~1`** 을 쓰면 안전하다.

## 2. 준비: 서버 상태 받아 오기 (fetch)

```bash
git fetch origin                 # 서버의 최신 상태를 origin/* 에만 받아 온다. 내 브랜치·파일은 안 바뀜
```

- 이 PC에서는 내부망 git 서버라 래퍼로 실행한다(승인 없이 실행되는 래퍼):
  ```powershell
  git fetch origin   # 사내망 전용 원격이면 회사 래퍼 스크립트로 실행
  ```
- `fetch`는 받기만 한다. `pull`(= fetch + merge)은 내 브랜치를 바꾸므로 체리픽 준비 단계에서는 쓰지 않는다.

### 로컬 브랜치를 서버에 맞추기 (빨리 감기)

```bash
git merge --ff-only origin/<릴리즈>    # 내 쪽에 다른 커밋이 없을 때만 서버 위치로 "앞으로 감기"
```

- `--ff-only`(fast-forward only): 단순히 이름표를 앞으로 옮길 수 있을 때만 성공한다. 내 로컬에만 있는 커밋이 있으면 **실패하고 아무것도 바꾸지 않는다** → 안전장치.

## 3. 워크트리(worktree): 폴더 하나 더 만들기

**왜 쓰나?** 지금 작업 폴더(`D:\work\myapp`, develop 개발 중)를 건드리지 않고, 다른 브랜치를 **별도 폴더**에 꺼내 작업하기 위해서다. 같은 저장소(.git)를 공유하므로 클론보다 빠르고 용량도 적다.

| 명령 | 하는 일 |
|---|---|
| `git worktree add C:\rel <릴리즈>` | `C:\rel` 폴더를 만들고 거기에 릴리즈 브랜치를 꺼낸다 |
| `git worktree add -b 새브랜치 C:\rel origin/<릴리즈>` | 서버 릴리즈 위치에서 **새 브랜치**를 만들어 꺼낸다 |
| `git worktree list` | 워크트리 목록과 각자 꺼낸 브랜치 확인 |
| `git -C C:\rel status` | `cd` 없이 그 폴더에서 git 명령 실행(`-C 폴더`) |
| `git worktree remove C:\rel` | 작업이 끝난 워크트리 삭제(미커밋 변경이 있으면 거부됨) |
| `git worktree prune` | 폴더를 손으로 지워 버렸을 때 남은 기록 정리 |

**이 저장소의 규칙과 이유**

- 워크트리는 **`C:\` 바로 아래**(예: `C:\rel`)에 만든다. 경로가 길면 namoEditor 파일에서 `Filename too long` 오류가 난다.
- **같은 브랜치를 두 폴더에 동시에 꺼낼 수 없다.** 작업 폴더가 이미 릴리즈를 꺼내 놓았다면 워크트리 추가가 거부된다 → `git worktree list`로 먼저 확인.
- 끝나면 `git worktree remove`로 지운다.

## 4. 체리픽(cherry-pick): 커밋 하나만 골라 복사하기

**개념:** 다른 브랜치의 특정 커밋이 만든 "변경분"만 떼어서 지금 브랜치 위에 새 커밋으로 붙인다. 원래 커밋과 **해시는 다르지만 내용(patch)은 같다.**

```
develop:     A ─ B ─ C ─ D
릴리즈:    X ─ Y
                └─ (cherry-pick C) → X ─ Y ─ C'
```

### 4-1. 반영할 커밋 찾기

```bash
# 릴리즈에 없는 develop 커밋, 병합 커밋 제외, 작성일 표시
git log --no-merges --format="%h %ad %an %s" --date=iso <릴리즈>..develop

# 오래된 것부터(체리픽 순서) 보기
git log --no-merges --reverse --format="%h %ad %s" --date=iso <릴리즈>..develop

# 특정 사람만 (이메일 기준이 정확함)
git log --no-merges --author="me@example.com" <릴리즈>..develop
```

| 옵션 | 뜻 |
|---|---|
| `--no-merges` | 병합 커밋 빼기 |
| `--reverse` | 오래된 것부터 출력 |
| `--format="..."` | 출력 모양 지정. `%h` 짧은 해시, `%s` 제목, `%an` 작성자, `%ad` **작성일**, `%cd` **커밋일** |
| `--date=iso` | 날짜를 `2026-10-27 14:00:00` 형태로 |
| `-- 파일경로` | 그 파일을 바꾼 커밋만 |

> **작성일(`%ad`) vs 커밋일(`%cd`)**: 체리픽·pull을 하면 커밋일은 그때로 바뀌고 작성일은 원래대로 남는다. 순서와 기간은 **작성일**로 판단한다. `git log --since`는 커밋일 기준이라 결과를 작성일로 다시 걸러야 한다.

### 4-2. 체리픽 실행

```bash
git cherry-pick abc1234                  # 커밋 하나
git cherry-pick abc1234 def5678 9a8b7c6  # 여러 개를 적은 순서대로
git cherry-pick -n abc1234               # --no-commit: 파일에만 적용하고 커밋은 안 함(시험 적용용)
```

### 4-3. 체리픽 도중 멈췄을 때 (충돌)

충돌이 나면 git이 멈추고 "conflict"를 알린다. 이때 할 수 있는 것:

| 명령 | 하는 일 | 언제 |
|---|---|---|
| `git status` | 충돌난 파일 목록(`both modified`) 확인 | 항상 제일 먼저 |
| `git diff` | 충돌 내용 보기 | 원인 파악 |
| `git add 파일` → `git cherry-pick --continue` | 충돌을 고쳤으니 계속 진행 | 고친 뒤 |
| `git cherry-pick --skip` | 이 커밋은 건너뛰고 다음으로 | 이미 반영된 내용일 때 |
| `git cherry-pick --abort` | **체리픽 시작 전 상태로 완전히 되돌림** | 원인을 모를 때, 선행 커밋이 필요할 때 |
| `git cherry-pick --quit` | 진행 상태 표시만 지우고 파일 변경은 그대로 둠 | 지금까지 결과를 백업 브랜치에 커밋해 두고 싶을 때 |

**충돌 표시 읽는 법**

```
<<<<<<< HEAD
지금 브랜치(릴리즈)에 있던 내용
=======
체리픽하려는 커밋이 넣으려는 내용
>>>>>>> abc1234 (커밋 제목)
```

> 체리픽에서 `HEAD`(=ours)는 **받는 쪽(릴리즈)**, 아래쪽(=theirs)은 **가져오는 커밋**이다.

**이 저장소의 충돌 규칙 (cherry-pick 스킬 2절)**

1. 충돌을 바로 고치지 않는다. 먼저 **그 줄을 만든 커밋**을 찾는다:
   ```bash
   git log -S "충돌 줄의 고유 문자열" <릴리즈>..develop -- 파일경로
   ```
   `-S "문자열"`(pickaxe): 그 문자열이 **생기거나 사라진** 커밋을 찾는다.
2. 릴리즈에 없는 **선행 커밋**이 필요하면 `--abort` 하고 사용자에게 보고 후 지시를 기다린다.
3. 같은 파일 끝에 각자 키를 덧붙인 경우(메시지 properties, config 등)만 양쪽을 모두 살린다.
4. 끝난 뒤 충돌 표시가 남았는지 반드시 검색한다(CRLF 파일은 표시가 남는 일이 있었다):
   ```bash
   git grep -n -e "^<<<<<<<" -e "^>>>>>>>" -e "^=======$"
   ```

## 5. 병합(merge): 브랜치 전체를 합치기

**개념:** 다른 브랜치의 커밋 **전부**를 지금 브랜치에 합친다. 두 부모를 가진 "병합 커밋"이 생긴다.
이 저장소의 병합 순서: **릴리즈 → master → develop** (master 병합 충돌은 develop 쪽 기준으로 푼다).

```
master:   M1 ─ M2 ─────── (병합커밋)
                         /
릴리즈:   R1 ─ R2 ─ R3 ─┘
```

| 명령 | 하는 일 |
|---|---|
| `git merge <릴리즈>` | 릴리즈를 지금 브랜치에 병합 |
| `git merge --ff-only origin/master` | 빨리 감기만 허용(2절) |
| `git merge --no-ff 브랜치` | 빨리 감기가 가능해도 병합 커밋을 꼭 만든다(이력 남기기) |
| `git merge --no-commit --no-ff 브랜치` | 병합 결과를 파일에만 만들고 커밋 전에 멈춤 → 확인 후 커밋 |
| `git merge --abort` | 충돌 중 병합을 취소하고 원래대로 |
| `git merge-base A B` | 두 브랜치가 갈라진 지점(공통 조상) 해시 |
| `git log --merges --oneline -5` | 최근 병합 커밋만 보기 |

**충돌 처리 흐름은 체리픽과 같다:** `git status` → 파일 수정 → `git add` → `git commit`(병합은 `--continue` 대신 커밋으로 마무리, `git merge --continue`도 가능).

**병합에서 조심할 것 (실제 있었던 일)**

- 충돌 해결 중 **기존 코드를 지워 버린** 사례(메일 메소드 약 180줄, 메시지 키).
- 충돌이 안 났는데도 **같은 블록이 두 번 들어가** SQL 괄호가 깨지거나 config 키가 중복된 사례.
- 그래서 병합 전후로 바뀐 SQL·properties·init 데이터를 비교한다:
  ```bash
  git diff 병합커밋~1 병합커밋 --stat          # 첫 부모(내 브랜치) 대비 무엇이 바뀌었나
  git diff 병합커밋~1 병합커밋 -- 경로/파일     # 파일 단위로 자세히
  ```

## 6. 체리픽 vs 병합, 언제 무엇을?

| | 체리픽 | 병합 |
|---|---|---|
| 가져오는 것 | 고른 커밋만 | 브랜치의 전부 |
| 용도 | develop → 릴리즈(필요한 수정만 골라 배포) | 릴리즈 → master → develop(전체 동기화) |
| 결과 커밋 | 새 해시의 복사본 | 병합 커밋 1개 + 원래 커밋들 |
| 주의 | 앞 커밋에 기대는 커밋은 단독으로 안 붙음 | 자동 병합이 조용히 중복·삭제를 만들 수 있음 |

## 7. 검증할 때 쓰는 명령

| 명령 | 하는 일 |
|---|---|
| `git show --stat abc1234` | 커밋이 바꾼 파일 목록과 줄 수 |
| `git diff --stat A B` | 두 지점 사이 바뀐 파일 목록 |
| `git show abc1234 \| git patch-id --stable` | 커밋 **내용의 지문**. 원 커밋과 체리픽 커밋의 값이 같으면 내용이 같다 |
| `git cherry -v <릴리즈> develop` | develop 커밋 중 릴리즈에 같은 내용이 있으면 `-`, 없으면 `+` 표시 |
| `git log --cherry-pick --right-only --no-merges <릴리즈>...develop` | 내용이 같은 짝을 빼고 develop에만 있는 커밋 |
| `git branch --contains abc1234` | 그 커밋을 포함한 브랜치 목록 |

> 함정: `git cherry`와 `--cherry-pick`은 **서로 도달할 수 없는 커밋끼리만** 비교한다. 체리픽 커밋이 병합으로 develop에도 들어와 있으면 짝을 못 찾는다. 이때는 제목이 같은 두 커밋을 `patch-id`로 직접 비교한다.

빌드 확인은 `mvn -q -o compile`(오프라인 컴파일)로 한다.

## 8. 되돌리기

| 명령 | 하는 일 | 안전도 |
|---|---|---|
| `git revert abc1234` | 그 커밋을 **반대로 하는 새 커밋**을 만든다. 이력은 그대로 | 안전. **이미 push한 브랜치는 이것만 쓴다** |
| `git revert -m 1 병합커밋` | 병합 커밋 되돌리기(1번 부모 기준) | 안전하지만 나중에 재병합이 까다로움 |
| `git reset --hard 커밋` | 브랜치를 그 커밋으로 강제로 옮기고 이후 변경을 버림 | **위험**. push 전 로컬에서만, 확인 후 |
| `git push --force` | 서버 이력을 덮어씀 | **이 저장소에서는 쓰지 않는다** |

> 다른 개발자도 릴리즈 브랜치에 직접 체리픽·push한다. 그래서 되돌리기는 revert 커밋으로만 하고, push 전에 다시 fetch해서 그사이 들어온 커밋을 확인한다.

## 9. 패치·번들로 옮기기 (사이트 전달용)

| 명령 | 하는 일 |
|---|---|
| `git format-patch -o 폴더 A..B` | A 이후 B까지의 커밋을 커밋당 `.patch` 파일 하나로 저장 |
| `git am --keep-non-patch 폴더/*.patch` | 패치 파일을 커밋으로 적용(작성자·제목·날짜 유지) |
| `git am --abort` | 적용 중 실패하면 취소 |
| `git bundle create 파일.bundle <릴리즈>` | 브랜치 이력을 파일 하나로 묶음 |
| `git clone 파일.bundle -b <릴리즈>` | 번들에서 저장소 복원 |

> `git am`을 옵션 없이 쓰면 제목 앞 `[FEATURE]` 같은 대괄호 태그가 지워진다. `--keep-non-patch`를 쓰면 `[PATCH 1/4]`만 지우고 나머지 태그는 남긴다. Git Bash에서는 경로를 `/c/...`가 아니라 `C:/...`로 준다.

## 10. 한눈에 보는 체리픽 전체 흐름 (예시)

```powershell
# 1) 서버 상태 받기
git fetch origin   # 사내망 전용 원격이면 회사 래퍼 스크립트로 실행

# 2) 반영할 커밋 고르기 (오래된 것부터)
git log --no-merges --reverse --format="%h %ad %an %s" --date=iso origin/release-1.0..origin/develop

# 3) 워크트리 만들기 (작업 폴더는 그대로 둠)
git worktree add C:\rel release-1.0
git -C C:\rel merge --ff-only origin/release-1.0

# 4) 체리픽 (작성일 순서대로)
git -C C:\rel cherry-pick abc1234 def5678

#    충돌 나면: git -C C:\rel status → 원인 확인(git log -S ...)
#    선행 커밋 필요 → git -C C:\rel cherry-pick --abort 후 보고
#    단순 겹침 → 양쪽 살려 수정 → git -C C:\rel add 파일 → git -C C:\rel cherry-pick --continue

# 5) 검증
git -C C:\rel grep -n -e "^<<<<<<<" -e "^>>>>>>>"
git show abc1234 | git patch-id --stable
git -C C:\rel show HEAD | git patch-id --stable     # 두 값 비교
# mvn -q -o compile (C:\rel 에서)

# 6) push는 사용자 승인 후에만 (inner-run 래퍼로)

# 7) 정리
git worktree remove C:\rel
```

## 11. 자주 하는 실수와 대처

| 증상 | 원인 | 대처 |
|---|---|---|
| 미반영 목록에 이미 넣은 커밋이 나온다 | 로컬 브랜치가 서버보다 뒤처짐 | fetch 후 `origin/<브랜치>` 기준으로 비교 |
| `fatal: '<릴리즈>' is already checked out` | 다른 폴더에 같은 브랜치가 꺼내져 있음 | `git worktree list`로 확인, 그 폴더를 쓰거나 새 브랜치로 꺼냄 |
| `Filename too long` | 워크트리 경로가 길다 | `C:\` 바로 아래에 만든다 |
| 체리픽 중 브랜치 전환이 안 됨 | 체리픽이 진행 중 상태 | `--continue`/`--abort`로 끝내거나 `--quit` 후 백업 브랜치에 커밋 |
| 체리픽 후 `>>>>>>>`가 파일에 남음 | CRLF 파일에서 충돌 표시 인식 오류 | 매번 `git grep`으로 충돌 표시 검색 |
| 커밋 하나 넣었는데 수십 개 파일이 충돌 | 앞선 미반영 커밋 위에서 만든 커밋 | `git log -S`로 선행 커밋 추적, 보고 후 지시 대기 |
| 기간 필터 결과가 이상함 | `--since`가 커밋일 기준 | `%ad`(작성일)로 다시 거름 |
| `git am` 후 제목의 `[FEATURE]`가 사라짐 | 옵션 없는 `git am`이 대괄호 태그 삭제 | `--keep-non-patch` 사용 |

## 12. 이 저장소에서 지키는 안전 규칙 요약

- `git push`는 **사용자 승인 후에만**, 그리고 force-push는 쓰지 않는다.
- 작업 폴더(develop 개발 중)는 건드리지 않고 워크트리에서 작업한다.
- 충돌은 원인(선행 커밋)부터 확인하고, 필요하면 멈추고 보고한다.
- `git diff`·`git show`로 볼 때도 비밀 설정 파일은 열람하지 않는다. 변경 경로는 `git status --short`로 얻어 경로를 지정해 본다.
