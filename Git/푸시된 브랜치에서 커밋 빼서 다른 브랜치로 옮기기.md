# 푸시된 브랜치에서 커밋 빼서 다른 브랜치로 옮기기

> 분류: Git · 최근 갱신: 2026-10-14

## 한 줄 요약
이미 push되어 다른 사람 커밋이 쌓인 브랜치에서는 force-push 대신 revert로 빼고, 옮길 브랜치에는 cherry-pick한다. 작업은 worktree에서 하고, revert 전에 "빠지는 코드를 아직 부르는 곳"을 반드시 확인한다.

## 내용
- **왜 revert인가**: 잘못 넣은 커밋 위에 다른 사람 커밋이 이미 올라간 공유 브랜치를 reset + force-push로 고치면 그 사람들의 로컬 이력이 꼬인다. `git revert`는 되돌리는 새 커밋을 추가하므로 이력을 다시 쓰지 않는다. 여러 커밋을 한 번에 되돌리려면 `--no-commit`으로 모아서 커밋 하나로 만든다.
- **revert 전에 확인할 것**: 되돌릴 커밋이 새로 추가한 함수·설정을, 그 뒤에 들어온 다른 커밋(또는 원래부터 있던 코드)이 호출하고 있을 수 있다. 충돌이 안 나도 실행 시 "is not defined" 같은 오류가 생긴다. 되돌릴 커밋이 추가한 식별자 목록을 뽑아 브랜치 전체에서 호출처를 검색하고, 필요한 정의는 남긴 채 revert한다.
- **충돌 없음 ≠ 안전**: 되돌린 뒤에 같은 파일을 다른 사람이 고쳤다면, 줄이 겹치지 않아 충돌은 없어도 그 수정이 되돌린 내용에 기대고 있을 수 있다. revert 전 그 파일들의 diff를 확인한다.
- **옮기는 범위 다시 세기**: 처음 체리픽이 "필요한 선행 커밋만" 고른 것이었다면, 옮길 때는 원래 작업 전체(같은 작업자·같은 주제의 커밋)를 다시 뽑아야 할 수 있다. 커밋 메시지 키워드로 고르면 키워드가 없는 커밋이 빠질 수 있다.
- **충돌 해결 원칙**: "옮기는 수정은 적용하되, 대상 브랜치에서 따로 바뀐 내용은 유지". 바뀐 줄이 대상 브랜치에 없는 기능 안에 있으면 적용하지 않는다.
- **worktree로 작업**: 사용 중인 작업 폴더를 건드리지 않고 브랜치별 폴더를 따로 만든다. `.git`을 공유하므로 원래 폴더에서도 그 브랜치 로그를 볼 수 있다.
- **"원격에 올렸는데 안 보인다"**: 대부분 로컬 브랜치가 pull을 안 받은 상태다. `git status`의 behind 개수와 로컬 전용 커밋 유무를 보면 fast-forward 가능 여부를 알 수 있다.

## 예시
```bash
# 작업용 worktree (Windows에서는 짧은 경로에)
git worktree add -b fix/rel-revert C:/wt-rel origin/release
git worktree add -b fix/move C:/wt-main origin/main

# 릴리즈: 여러 커밋을 revert 커밋 하나로
cd C:/wt-rel
git revert --no-commit <첫커밋>^..<마지막커밋>
git checkout HEAD -- <남겨야 할 정의가 있는 파일>   # 필요하면 일부만 되살린 뒤 확인
git commit -m "Revert: ... (main으로 이동)"

# 메인: 같은 커밋들을 순서대로 (원 작성자 유지됨)
cd C:/wt-main
git cherry-pick <커밋1> <커밋2> ...

# 정리
git worktree remove C:/wt-rel
git branch -D fix/rel-revert
```
변경된 JS 파일 문법만 빠르게 검사: `node --check 파일.js`

## 주의할 점
- Windows에서 worktree를 깊은 임시 폴더에 만들면 긴 파일명 때문에 "Filename too long"으로 체크아웃이 실패할 수 있다. 짧은 경로를 쓰거나 `core.longpaths`를 켠다.
- push 직전에 원격을 다시 fetch해서 그 사이 올라온 커밋이 없는지 확인한다.
- 일부만 남기는 revert(`checkout HEAD -- 파일`)를 하면 그 파일의 다른 변경까지 남으므로, 남길 부분만 손으로 정리하는 편이 정확하다.
- 정적 검사(충돌 마커, JS 문법, 정의 없는 함수 호출)는 화면 동작 확인을 대신하지 못한다.
