# 브랜치 간 미반영 커밋 찾기(작성자·커미터·patch-id)

> 분류: Git · 최근 갱신: 2026-10-21

## 한 줄 요약
"개발 브랜치에는 있는데 릴리즈 브랜치에는 없는 내 커밋"을 뽑을 때는 해시 비교만으로는 부족하다. 날짜 두 종류, 작성자와 커미터, 한 사람의 여러 표기, 체리픽으로 바뀐 해시를 모두 고려해야 한다.

## 내용
### 날짜가 두 개다
- 커밋에는 작성일(author date)과 커밋일(committer date)이 있다. 체리픽·rebase·amend를 하면 커밋일만 새로 바뀐다.
- `git log --since/--until`은 커밋일 기준이고, 날짜가 뒤섞인 이력에서는 순회를 일찍 끝내 커밋을 빠뜨릴 수 있다. 비교 범위 전체를 받은 뒤 프로그램에서 원하는 날짜로 거르는 편이 안전하다.

### 작성자와 커미터가 다르다
- 체리픽하면 작성자는 원래 개발자로 남고 커미터는 옮긴 사람이 된다. `--author`로만 거르면 "내가 옮긴 남의 커밋"은 빠지고, `--committer`로만 거르면 "남이 옮긴 내 커밋"이 빠진다. 목적에 맞게 작성자·커미터·둘 중 하나를 고른다.

### 한 사람이 여러 표기로 커밋한다
- 대소문자만 다른 이름, 개인·회사 이메일 등 이름·이메일 조합이 여럿이다. "표시 이름 1개 ↔ 이메일·이름 여러 개" 매핑을 두고 이메일을 기본 키로 쓴다. `git shortlog -sne --all`로 전체 조합을 본다. 공식 기능으로는 `.mailmap`이 있다.

### 반영 판정 단계
1. 해시가 비교 브랜치에 있다 → 반영
2. 변경 내용이 같다(patch-id 일치) → 체리픽으로 반영
3. 내용은 다르고 제목만 같다 → 충돌을 풀어 넣은 것으로 보고 따로 표시
4. 어디에도 없다 → 미반영
- 머지 커밋은 빼고, Revert와 원 커밋의 짝은 따로 표시한다.

### --cherry-pick이 짝을 못 찾는 경우
- `git log --cherry-pick --right-only A...B`는 대칭 차집합 안에서만 patch-id를 비교한다. 릴리즈→master→개발 순서로 병합해 오는 구조에서는, 릴리즈에 체리픽된 사본이 병합을 통해 이미 개발 브랜치 이력에도 들어와 있어 차집합에서 빠지고, 원 커밋만 남아 짝을 찾지 못한다.
- 그래서 미반영 후보 중 제목이 같은 커밋이 비교 브랜치에 있으면, 두 커밋의 patch-id를 직접 계산해 비교한다. 같으면 체리픽으로 판정한다.

### 걸러지지 않는 것
- 제목을 바꿔 넣은 커밋, 여러 커밋을 합쳐 넣은 커밋, 개발 브랜치 전용 설정 커밋은 사람이 봐야 한다.
- 같은 변경이 개발 브랜치에 두 번 들어간 경우(같은 제목·같은 변경)는 하나만 옮기면 된다.

## 예시
```bash
git fetch --prune origin                                    # 원격 기준으로 비교 (로컬 브랜치는 안 바뀜)
git log --no-merges --format='%H|%an|%ae|%ad|%cn|%ce|%cd|%s' --date=iso origin/release..origin/dev
git log --cherry-pick --right-only --no-merges origin/release...origin/dev
git show <커밋> | git patch-id --stable                      # 커밋 하나의 patch-id
git shortlog -sne --all                                      # 이름·이메일 조합 목록
```

## 주의할 점
- 로컬 브랜치가 원격보다 뒤처져 있을 수 있으니 `origin/<브랜치>`로 비교하고, 로컬에만 있는(push 안 한) 커밋은 따로 표시한다.
- 결과를 엑셀 등으로 넘길 때 "어느 날짜 기준으로 걸렀는지"를 함께 적는다.
