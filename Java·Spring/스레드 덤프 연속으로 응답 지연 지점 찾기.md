# 스레드 덤프 연속으로 응답 지연 지점 찾기

> 분류: Java·Spring · 최근 갱신: 2026-11-10

## 한 줄 요약
화면 하나가 몇 초씩 걸릴 때, 요청별 시간을 재서 느린 요청을 고른 뒤 그 요청이 도는 동안 스레드 덤프를 1초 간격으로 여러 번 떠서 같은 스택에 머무는 곳을 찾으면 "어디서 기다리는지"가 나온다.

## 내용
- 개발 PC·시험 서버에서는 운영과 달리 SSO·메일·외부 API 서버에 닿지 않는 경우가 많다. 이때 로그인이나 첫 화면이 연결 타임아웃만큼 멈추는데, 로그에는 아무것도 안 남거나 한참 뒤에 실패 한 줄만 남는다.
- 순서
  1. 브라우저 자동화나 개발자 도구로 요청별 시간을 재서 느린 요청만 고른다(나머지가 빠르면 DB 문제가 아니다).
  2. 그 요청을 다시 보내면서 `jstack <pid>`를 1초 간격으로 5~10번 뜬다.
  3. 요청 처리 스레드(톰캣이면 `http-nio-<포트>-exec-*`)의 스택을 비교한다. 여러 덤프에서 같은 프레임(`SocketInputStream.read`, `PlainSocketImpl.connect`, `getStore` 등)에 머물면 그 위의 애플리케이션 프레임이 기다리는 호출이다.
- 결과 해석
  - `connect`에서 멈춤 → 상대 서버에 닿지 않음(방화벽, 망 분리). 연결 타임아웃 값만큼 기다린다.
  - `read`에서 멈춤 → 연결은 됐지만 응답이 느림.
  - 같은 요청에서 외부 호출이 여러 개 순서대로 나오면 시간은 더해진다(예: 2초 + 2초 + 3초).
- 실패 결과를 캐시하는 호출은 첫 요청만 느리고 다음부터 빨라지므로, 측정은 새 세션·새 사용자로 여러 번 한다.
- 성능 개선을 잴 때는 이런 외부 대기 구간을 따로 표시해 빼고 본다. 운영에서도 느리다면 같은 지점(외부 서버 주소·포트 설정)을 먼저 확인한다.

## 핵심 코드
```powershell
# Windows: 1초 간격으로 덤프 10개 (pid는 jps -l 이나 작업 관리자로 확인)
$javaPid = 12345
1..10 | ForEach-Object {
  & jstack $javaPid > ("dump-{0:D2}.txt" -f $_)
  Start-Sleep -Seconds 1
}
```

```bash
# Linux
pid=12345
for i in $(seq -w 1 10); do jstack "$pid" > "dump-$i.txt"; sleep 1; done
# 요청 처리 스레드에서 애플리케이션 패키지 프레임만 모아 자주 나오는 순으로
grep -h -A30 '"http-nio-' dump-*.txt | grep 'at com\.example\.' | sort | uniq -c | sort -rn | head
```

```javascript
// Playwright: 요청별 소요 시간 기록 (느린 요청 고르기)
page.on('requestfinished', req => {
  const t = req.timing();
  const ms = t.responseEnd - t.startTime;
  if (ms > 500) console.log(Math.round(ms), req.url());
});
```

## 주의할 점
- 덤프 한 장으로는 "지나가던 순간"인지 "머무는 곳"인지 구분할 수 없다. 여러 장에서 반복되는 프레임만 믿는다.
- 운영 서버에서 덤프를 뜨면 순간 멈춤이 생길 수 있으니 짧은 간격·적은 횟수로 한다.
- 덤프에는 요청 파라미터나 내부 주소가 섞일 수 있으니 공유할 때 가린다.
- 시간 제한 자체를 손볼 때는 [Future로 외부 호출 전체 시간 제한하기](Future로 외부 호출 전체 시간 제한하기.md)와 [외부 API 판정 결과의 로컬 캐시 설계](외부 API 판정 결과의 로컬 캐시 설계.md)를 함께 본다.
