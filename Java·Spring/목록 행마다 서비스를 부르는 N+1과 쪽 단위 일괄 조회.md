# 목록 행마다 서비스를 부르는 N+1과 쪽 단위 일괄 조회

> 분류: Java·Spring · 최근 갱신: 2026-11-04

## 한 줄 요약
목록을 그리는 반복문 안에서 행마다 서비스(읽음 여부, 댓글 수, 첨부 등)를 부르면, 쿼리 하나는 빨라도 호출마다 붙는 트랜잭션·커넥션 검증 왕복 때문에 행 수에 비례해 느려진다. 쪽에 나온 ID 목록으로 한 번씩 조회해 Map으로 찾아 쓰면 결과는 그대로이고 호출 수만 줄어든다.

## 내용
### 알아보는 방법
- 같은 화면에서 행이 2개인 마지막 쪽과 50개인 쪽의 응답 시간을 비교한다. 행 수에 비례해 늘면(예: 행당 수십 ms) N+1이다. 목록 쿼리 자체의 시간을 따로 재서 그 차이를 확인한다.
- 행마다 하는 추가 조회가 없는 다른 목록(같은 쿼리, 같은 행 수)과 비교해도 된다.

### 쿼리는 빠른데 호출이 느린 이유
- Spring에서 `*ServiceImpl` 메소드에 트랜잭션 AOP가 걸려 있으면 호출마다 커넥션을 꺼내고 트랜잭션을 시작·커밋한다.
- 커넥션 풀이 꺼낼 때마다 검증하면(`testOnBorrow=true`, `validationQuery="select 1"`) 왕복이 하나 더 붙는다.
- 그래서 7~9ms짜리 쿼리 하나가 호출로는 20ms가 넘고, 행마다 2~3번 부르면 행당 40~60ms가 된다. WAS와 DB 사이 지연이 클수록(원격·무선) 더 커진다. 운영처럼 가까워도 왕복 수는 같다.

### 고치는 방법
- 목록 쿼리를 받은 직후 쪽의 ID를 모아 `IN (...)`으로 한 번씩 조회하고, 결과를 `Map<ID, 값>`이나 `Set<ID>`로 만든다. 반복문에서는 DB 대신 Map을 찾는다.
- 판정 조건은 기존 단건 쿼리와 똑같이 둔다. 예: 읽음 여부를 (게시판ID, 글ID) 쌍으로 판정했다면 일괄 조회도 쌍 키로 판정한다. 결과에 없는 ID의 기본값(0, false)도 원래 동작과 맞춘다.
- 목록 쿼리에 서브쿼리로 넣는 방법도 있지만, 큰 쿼리를 DB별로 고쳐야 하고 정렬 전 모든 행에 붙을 수 있다. 별도 일괄 조회 몇 개가 영향 범위가 작다.
- 기존 단건 메소드와 쿼리는 다른 곳에서 쓰므로 지우지 않고 새 메소드를 더한다.

### 같은 값을 칸마다 다시 읽는 경우
- 행×열마다 부르는 셀 변환 함수가 첫머리에서 설정값(테넌트 설정 등)을 DB로 읽으면, 15행×10열 목록에서 같은 값을 150번 읽는다. 그 값이 필요한 열이 몇 개뿐이어도 그렇다.
- 고치는 방법: ① 값이 필요한 열에서만 읽고, ② 값을 인자로 받는 오버로드를 추가해 목록 루프 앞에서 한 번 읽어 넘긴다. 기존 시그니처는 새 오버로드에 위임해 다른 호출처는 그대로 둔다.

### 화면 트리에서 노드마다 하는 확인 요청 (프런트 쪽 N+1)
- 지연 로딩 트리가 노드를 그릴 때마다 "이 사용자가 볼 수 있는 하위가 있는지"를 동기 AJAX로 확인하면, 그룹 하나를 펼칠 때 하위 있는 자식 수만큼 요청이 순서대로 나간다. 요청 하나가 빨라도(30~50ms, 그중 절반은 매 요청 공통 비용) 수가 쌓인다.
- 고치는 방법: 목록 응답을 받으면 확인이 필요한 자식 ID를 모아 **일괄 요청 한 번**으로 Y/N을 받고, 기존 확인 함수가 그 결과를 먼저 보게 한다. 서버는 기존 단건 판정 로직을 그대로 반복해 같은 결과를 보장한다. 일괄 요청이 실패하면 노드별 확인으로 돌아가게 한다.
- 일괄 엔드포인트는 ID 형식 검사와 개수 상한(예: 200)을 둔다.
- 검증은 두 방식으로 그린 화면을 비교한다: 일괄 요청을 막아 기존 방식으로 그린 트리와 새 방식 트리의 노드별 상태가 모두 같은지.

### 일괄 조회가 기대는 인덱스
- 단건 조회는 PK(예: 게시판ID, 글ID, 사용자ID)를 탔더라도, 일괄 조회가 `사용자ID AND 글ID IN (...)`처럼 PK 앞 컬럼을 빼고 찾으면 PK를 앞부분까지만 쓴다. 그러면 사용자 기준 인덱스가 없는 DB에서 테이블을 크게 훑어 오히려 느려질 수 있다.
- 새 인덱스를 전체 DDL에만 넣고 기존 사이트용 패치 스크립트에 빠뜨리기 쉽다. 일괄 조회를 넣을 때 그 인덱스가 패치 경로에도 있는지 확인하거나, 조건에 PK 앞 컬럼을 함께 넣는다.

### 2) IN 목록 나누기 (Oracle 1000개 제한)
```java
public Map<String, Integer> countCommentsByItem(List<String> ids) {
    Map<String, Integer> result = new HashMap<>();
    for (int i = 0; i < ids.size(); i += 500) {
        List<String> part = ids.subList(i, Math.min(i + 500, ids.size()));
        if (part.isEmpty()) continue;
        for (Map<String, Object> row : commentDao.countByItemIds(part)) {
            result.put((String) row.get("itemId"), ((Number) row.get("cnt")).intValue());
        }
    }
    return result;
}
```

### 4) 트리 노드 확인을 일괄 요청으로 (JavaScript)
```javascript
var visibleSubCache = {};                       // boardId -> "Y" | "N"
function prefetchVisibleSubs(nodes) {
  var ids = nodes.filter(function (n) { return n.hasChildren && !(n.id in visibleSubCache); })
                 .map(function (n) { return n.id; });
  if (ids.length === 0) return;
  $.ajax({ url: "/api/boards/visible-children", type: "POST", async: false,
           data: { ids: ids.join(",") }, dataType: "json" })
   .done(function (res) { $.extend(visibleSubCache, res); });   // 실패하면 캐시 없음 → 기존 방식
}
function hasVisibleChildren(boardId) {           // 기존 노드별 확인 함수
  if (boardId in visibleSubCache) return visibleSubCache[boardId] === "Y";
  return legacyCheckOne(boardId);                // 기존 단건 요청
}
```

### 5) 일괄 판정 서버 (Java)
```java
@PostMapping("/api/boards/visible-children")
@ResponseBody
public Map<String, String> visibleChildren(@RequestParam String ids, HttpServletRequest req) {
    List<String> list = Arrays.asList(ids.split(","));
    if (list.size() > 200 || !list.stream().allMatch(s -> s.matches("[A-Za-z0-9_-]{1,64}"))) {
        throw new IllegalArgumentException("bad ids");
    }
    UserInfo user = auth.currentUser(req);
    Map<String, String> out = new LinkedHashMap<>();
    for (String id : list) {
        out.put(id, boardService.findVisibleChildren(id, user).isEmpty() ? "N" : "Y"); // 기존 판정 그대로
    }
    return out;
}
```

## 주의할 점
- 바꾼 뒤 응답이 같은지 확인한다. 수정 전 응답(여러 계정·게시판 종류·쪽)을 저장해 두고, 수정 후 같은 요청의 응답과 글자 단위로 비교하면 확실하다.
- 같은 반복 조회가 다른 목록(검색 결과, Q&A 목록 등)에도 있는지 찾아본다. 한 곳만 고치면 그 화면만 빨라진다.
- 실행 계획은 테스트 DB의 데이터 규모로는 차이가 안 날 수 있다. 읽은 행 수(`ANALYZE`의 r_rows, `EXPLAIN`의 rows)로 판단한다.
