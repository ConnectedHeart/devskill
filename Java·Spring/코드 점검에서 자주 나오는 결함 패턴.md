# 코드 점검에서 자주 나오는 결함 패턴

> 분류: Java·Spring · 최근 갱신: 2026-11-03

## 한 줄 요약
컴파일과 문법 검사는 통과하지만 실행 중에 문제가 되는 패턴들 — 순회 중 삭제, 예외 삼킴, 확장자 판별, 프록시를 거치지 않는 내부 호출, 문자열 `==` 비교, null 확인 순서, 단위 계산 인덱스, 기본값 if 블록에 갇힌 검사, 검증 뒤 `return` 누락, 뒤집힌 조건.

## 내용
### 순회 중 삭제 (ConcurrentModificationException)
- 컬렉션을 for-each로 돌면서 같은 컬렉션에서 항목을 지우면 `ConcurrentModificationException`이 난다.
- 라이브러리의 getter가 복사본이 아니라 **내부 리스트를 그대로 반환**하는 경우, 그 객체의 삭제 메서드를 순회 중에 호출해도 같은 일이 생긴다. 반환값이 복사본인지는 `javap`나 소스로 확인한다.
- 해결: 지울 항목을 따로 모았다가 순회가 끝난 뒤 삭제하거나, `Iterator.remove()` / `removeIf`를 쓴다.

### 예외를 삼키는 catch
- `catch (Exception e) { continue; }`는 위와 같은 버그를 로그 없이 넘겨서, 결과물에서 일부 항목만 조용히 빠진다.
- catch 범위를 예상하는 예외로 좁히고, 넘어가더라도 로그는 남긴다.

### 파일 확장자 판별
- "뒤 3글자"로 확장자를 판별하면 4글자 확장자(`docx`, `hwpx`, `jpeg`)가 잘려 엉뚱한 값이 된다. 마지막 `.` 뒤를 잘라 쓴다.
- 확장자를 문자열 치환으로 바꾸면(`.hwp` → `.pdf`) 앞부분이 같은 다른 확장자가 `a.hwpx` → `a.pdfx`처럼 깨진다.
- 비교할 때 점 포함 여부(`"pdf"` vs `".pdf"`)와 대소문자를 코드 전체에서 통일한다.
- 새 형식을 추가할 때는 기존 형식만 처리하던 분기(복원, 변환, 일괄 처리)를 모두 찾아야 한다. 한쪽만 고치면 기존 형식 문서가 회귀한다.

### 같은 이름인데 대소문자가 다른 식별자
- 찾을 때와 지울 때 쓰는 이름의 대소문자가 다르면 찾기는 성공하고 지우기는 실패하는 식의 반쪽 동작이 된다. 상수로 빼서 한 곳에서 관리한다.

### Spring 프록시를 거치지 않는 내부 호출
- `@Async`, `@Transactional` 같은 애너테이션은 프록시를 통해 호출될 때만 적용된다.
- 같은 클래스 안에서 `this.method()`로 부르면 프록시를 거치지 않아 `@Async` 메서드도 호출한 스레드에서 그대로 이어서 실행된다.
- 의도한 동작인지 확인하고, 분리해야 하면 다른 빈으로 옮긴다.

### 설정값을 `==`로 비교
- `Properties`나 파일에서 읽은 문자열을 `useFlag == "YES"`로 비교하면 항상 false다(문자열 리터럴과 다른 객체). 그 분기 안의 코드는 한 번도 실행되지 않지만 오류도 없다.
- `"YES".equalsIgnoreCase(useFlag)`처럼 리터럴을 앞에 두면 null에도 안전하다. 같은 클래스의 다른 곳이 어떻게 비교하는지 보고 통일한다.
- 이런 분기를 고쳐서 처음으로 실행되게 만들면, 그 안에 숨어 있던 다른 버그(파라미터 키 불일치 등)가 같이 드러난다. 한 번에 끝까지 따라가 본다.

### null 확인 순서
- `!s.equals("") && s != null`은 `equals`가 먼저 호출되어 null이면 NPE가 난다. null 확인을 항상 맨 앞에 둔다: `s != null && !s.equals("")`.
- 목록 파라미터에 `required = false`를 주고 `list.remove(0)`을 null·크기 확인보다 먼저 호출하는 것도 같은 종류다. 확인 조건 안으로 옮기고, "0번 자리를 비워 두는" 관례가 있다면 `size() > 1`로 조건을 맞춘다.

### 단위 계산의 배열 인덱스
- 파일 크기를 `(int)(log10(size) / log10(1024))`로 단위 배열(`bytes/KB/MB/GB`) 인덱스를 구하면 0바이트는 `log10(0) = -∞`로 큰 음수, TB 이상은 4가 되어 `ArrayIndexOutOfBounds`가 난다. 빈 문자열은 `parseDouble`에서 예외다.
- 0 이하는 0으로, 결과를 `0 ~ length-1`로 clamp하고, 파싱 예외는 0으로 처리하는 메서드 하나로 묶는다. 같은 계산이 여러 곳에 복사돼 있으면 모두 그 메서드로 바꾼다.

### 루프 안에서 메서드 파라미터에 대입
- "넘겨받은 값이 null이면 수신자 설정을 조회해 채운다"를 **파라미터 변수에 직접 대입**하면, 첫 반복에서 채워진 값이 두 번째 반복부터 그대로 쓰인다(null이 아니므로 다시 조회하지 않음). 결과적으로 첫 대상의 설정이 모든 대상에 적용된다.
- 컬렉션이 `HashSet`이면 "첫 대상"도 실행마다 달라져 재현이 들쭉날쭉하다.
- 반복마다 새 지역 변수에 담는다. 파라미터에 재대입하지 않는 규칙(`final` 파라미터, 정적 분석의 "parameter reassignment" 경고)으로 미리 막을 수 있다.
- 지역 변수는 **초기값 없이 선언하고 모든 분기에서 대입**한다. `= null`로 시작하면 분기 하나를 빠뜨려도 컴파일되고 실행 중 NPE로만 드러나지만, 초기값이 없으면 컴파일러의 definite assignment 검사가 바로 오류를 낸다.

### 래퍼가 받은 인자를 전달하지 않음
- 오버로드를 하나 늘리면서 비동기 래퍼 같은 중간 메서드의 시그니처에는 인자를 추가했는데, 안에서 부르는 줄은 옛 오버로드 그대로 남는 경우가 있다. 호출하는 쪽이 무엇을 넘겨도 무시된다.
- 새 인자를 추가한 커밋에서 그 인자를 받는 모든 메서드가 실제로 값을 넘기는지 확인한다. `git blame`으로 시그니처와 호출 줄이 같은 커밋에서 바뀌었는지 보면 누락을 알 수 있다.

### 검증 alert 뒤 `return` 누락 (JS)
- 저장 버튼 핸들러에서 필수값 검사 여러 개 중 하나만 `alert` 뒤에 `return`이 없으면, 안내는 뜨는데 저장은 그대로 진행된다. 변수에 남아 있던 이전 값이 저장되어 사용자는 무엇이 저장됐는지 알 수 없다.
- 같은 함수의 다른 검사들과 형태를 나란히 놓고 비교하면 바로 보인다.

### 기본값 대입 if 블록에 검사까지 들어간 괄호 위치
- "값이 비어 있으면 기본값을 넣는다" if 블록의 닫는 괄호가 뒤로 밀려, 그 아래 비교·검사 코드까지 블록 안에 들어가는 경우가 있다. 그러면 검사는 **값이 비어 있던(기본값이 들어간) 경우에만** 돌고, 정작 값이 있는 대상은 검사를 건너뛴다.
- 예: 사용자 보안등급이 비면 0(모두 허용)으로 바꾸는 블록 안에 등급 비교가 들어 있으면, 비교는 항상 허용인 사용자에게만 돌고 등급이 있는 사용자는 무조건 통과한다.
- 같은 일을 하는 쌍둥이 메서드(완료용·진행용 등)가 있으면 나란히 놓고 괄호 위치를 비교하면 바로 보인다. 공백을 무시한 diff(`git diff -w`)로 보면 "닫는 괄호 하나 이동"만 남는지 확인할 수 있다.
- 고치면 그동안 건너뛰던 검사가 처음으로 돌기 시작한다. 그 검사 안의 숨은 문제(숫자가 아닌 값의 `parseInt` 예외, 예외 설정이 꺼진 환경에서 업무가 막히는 경우)가 같이 드러나므로 영향 범위를 함께 확인한다.

### 뒤집힌 조건과 의도 추정
- `if (input.val() != "") input.val(saved)`처럼 "값이 있을 때만 기존 값으로 덮어쓰는" 코드는 사용자가 고친 내용만 되돌리는 동작이 된다. 작성자 의도는 `== ""`(비어 있으면 채움)였을 가능성이 크다.
- 그러나 뒤집어도 실제로 동작하는 경우가 거의 없다면(초기화를 다른 함수가 이미 함) 블록을 지우는 쪽이 더 단순하다. `git log -L`로 작성 시점과 메시지("개발중" 등)를 보면 정리되지 않은 코드인지 판단에 도움이 된다.

## 핵심 코드
### 1) 순회 중 삭제 피하기
```java
// 순회 후 삭제
List<Item> toRemove = new ArrayList<>();
for (Item item : parent.items()) {
    if (shouldRemove(item)) toRemove.add(item);
}
toRemove.forEach(parent::removeItem);

// 직접 가진 컬렉션이면
items.removeIf(this::shouldRemove);
for (Iterator<Item> it = items.iterator(); it.hasNext(); ) {
    if (shouldRemove(it.next())) it.remove();
}
```

### 2) 예외는 좁게 잡고 넘어가더라도 로그
```java
for (Item item : items) {
    try {
        process(item);
    } catch (IOException e) {                  // Exception 전체가 아니라 예상한 예외만
        log.warn("skip item {}", item.getId(), e);
    }
}
```

### 3) 확장자 판별과 교체
```java
// 확장자
int dot = name.lastIndexOf('.');
String ext = dot < 0 ? "" : name.substring(dot + 1).toLowerCase();

// 교체: 문자열 치환 대신 마지막 '.' 앞을 잘라 붙인다 (a.hwpx → a.pdf)
static String replaceExt(String name, String newExt) {
    int i = name.lastIndexOf('.');
    return (i < 0 ? name : name.substring(0, i)) + "." + newExt;
}
```

### 4) 문자열 비교와 null 확인 순서
```java
private static final String ITEM_NAME = "Summary";        // 찾기·지우기에 같은 상수

if ("YES".equalsIgnoreCase(useFlag)) { ... }               // == 금지, 리터럴을 앞에 → null 안전

```

### 5) 파일 크기 표시 (인덱스 clamp)
```java
// 파일 크기 표시
static String formatSize(String raw) {
    String[] unit = {"bytes", "KB", "MB", "GB"};
    double size;
    try { size = Double.parseDouble(raw); } catch (NullPointerException | NumberFormatException e) { size = 0; }
    int idx = size > 0 ? (int) (Math.log10(size) / Math.log10(1024)) : 0;
    idx = Math.max(0, Math.min(idx, unit.length - 1));
    return String.format("%.1f", size / Math.pow(1024, idx)) + unit[idx];
}
```

### 6) `@Async`·`@Transactional`이 적용되게 다른 빈으로 분리

```java
        this.worker = worker;
    }

    public void request(String id) {

    }
}

@Service
public class MyAsyncWorker {
    @Async
    public void build(String id) { ... }
}
```

### 6-1) 반복마다 지역 변수로 판정 (파라미터 재대입 금지)
```java
public void send(Set<User> users, Set<Channel> allowedChannels) {
    for (User user : users) {
        Set<Channel> channels;                       // 초기값 없음 → 분기 누락 시 컴파일 오류
        if (allowedChannels != null) {
            channels = allowedChannels;              // 호출자가 지정한 값
        } else if (user.isForced()) {
            channels = EnumSet.allOf(Channel.class);
        } else {
            channels = settingService.findChannels(user.getId());   // 사용자마다 조회
        }
        deliver(user, channels);
    }
}
```

### 6-2) 래퍼는 받은 인자를 그대로 넘긴다
```java
@Async
public void sendAsync(List<User> users, String content, Set<Channel> channels) {
    notifyService.send(users, content, channels);    // channels를 빠뜨리고 옛 오버로드를 부르면 항상 null
```

### 6-3) 기본값 대입 블록은 대입만 하고 바로 닫는다
```java
// 잘못: 비교가 if 안에 있어 값이 있는 사용자는 검사를 건너뜀
if (userLevel == null || userLevel.trim().isEmpty()) {
    userLevel = "0";
    allowed = Integer.parseInt(userLevel) <= docLevel;
}

// 수정: 기본값만 넣고 닫은 뒤 모든 사용자에게 비교
if (userLevel == null || userLevel.trim().isEmpty()) {
    userLevel = "0";
}
allowed = Integer.parseInt(userLevel.trim()) <= docLevel;   // 숫자가 아닌 값은 따로 검증
```

## 주의할 점
- 변경 파일이 많은 점검은 기계적 검사(컴파일, `node --check`)를 먼저 돌리고, 로직 검토는 관점을 정해서 본다: 분기 누락으로 인한 null, 하드코딩된 값, 비교 방식 불일치, 기존 데이터 회귀.
- 문법 검사 통과는 로직이 맞다는 뜻이 아니다. 실제 파일로 실행해 보기 전에는 "확인됨"으로 적지 않는다.
