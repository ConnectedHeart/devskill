# 싱글턴 빈 필드에 사용자별 상태를 두면 생기는 문제

> 분류: Java·Spring · 최근 갱신: 2026-11-16

## 한 줄 요약
Spring 서비스 빈은 기본이 싱글턴이라 필드에 "현재 사용자의 API 클라이언트·인증 흐름"을 담아 두면 동시 요청끼리 덮어써 다른 사람 데이터가 섞이고, 서버가 여러 대면 다음 요청이 다른 서버로 가서 상태를 잃는다. 요청 안에서 만들어 지역 변수로 쓴다.

## 내용
- **증상**
  - 외부 API(캘린더 등)를 사용자 토큰으로 부르는 서비스가 `service = buildClient(user)`처럼 필드에 클라이언트를 넣고 다음 줄에서 `service.list()`를 부르면, 그 사이 다른 요청이 필드를 바꿔 **A 사용자 화면에 B의 데이터**가 나올 수 있다. 부하가 적을 때는 거의 안 나타나 시험으로 잡기 어렵다.
  - OAuth 인증 흐름 객체를 첫 요청(인증 시작)에서 필드에 만들어 두고 콜백 요청에서 꺼내 쓰면, 콜백이 다른 WAS로 가거나 서버가 재기동되면 필드가 비어 연동이 실패한다.
  - 클라이언트 생성이 실패해도 예외를 삼키면 **이전 사람의 클라이언트**가 필드에 남아 그대로 쓰인다.
- **고치는 방법**
  - 사용자별 객체는 메소드 안에서 만들어 반환값·지역 변수로만 넘긴다. 메소드 시그니처를 유지하면 호출부는 고칠 필요가 없다.
  - 인증 흐름처럼 설정값만으로 다시 만들 수 있는 객체는 요청마다 설정으로 새로 만든다. 사용자별 진행 상태(state 값 등)는 DB나 세션처럼 모든 서버가 보는 곳에 둔다.
  - 빈 필드에 남겨도 되는 것은 설정·스레드 안전한 공용 객체(HTTP 전송 객체, JSON 파서 등)뿐이다.
- **찾는 요령**: `@Service`·`@Component` 클래스에서 `final`이 아니고 메소드 안에서 대입되는 필드를 찾는다. 필드를 지운 뒤 컴파일하면 참조하던 곳이 모두 드러난다.

## 핵심 코드
```java
// 전: 필드에 사용자별 클라이언트 (동시 요청이 서로 덮어씀)
@Service
public class CalendarServiceImpl implements CalendarService {
    private Calendar client;                         // 위험

    public List<Event> listEvents(LoginUser user, String day) throws IOException {
        client = buildClient(user);                  // 다른 요청이 여기서 바꿀 수 있음
        return client.events().list("primary").execute().getItems();
    }
}
```
```java
// 후: 요청 안에서 만들고 지역 변수로만 사용
@Service
public class CalendarServiceImpl implements CalendarService {
    private static final JsonFactory JSON = GsonFactory.getDefaultInstance();  // 공용·불변은 OK

    public List<Event> listEvents(LoginUser user, String day) throws IOException {
        Calendar client = buildClient(user);         // 실패하면 예외 → 호출부 오류 처리로
        return client.events().list("primary").execute().getItems();
    }

    private Calendar buildClient(LoginUser user) throws IOException {
        Credential cred = loadCredential(user.getUserId());   // DB에 저장된 토큰
        return new Calendar.Builder(transport(), JSON, cred).setApplicationName("my-app").build();
    }

    private AuthorizationCodeFlow buildAuthFlow() {          // 콜백이 어느 서버로 와도 같은 결과
        return new GoogleAuthorizationCodeFlow.Builder(transport(), JSON,
                config.clientId(), config.clientSecret(), SCOPES).build();
    }
}
```

## 주의할 점
- `@Scope("prototype")`으로 바꿔도 싱글턴 빈에 주입되면 한 번만 만들어지므로 해결되지 않는다. 지역 변수가 가장 단순하다.
- `ThreadLocal`로 우회하면 스레드 풀 재사용 때 값이 남는 위험이 생긴다. 반드시 finally에서 지워야 한다.
- 단위 테스트로는 동시성 섞임을 재현하기 어렵다. 리뷰와 정적 검색으로 막는다.
