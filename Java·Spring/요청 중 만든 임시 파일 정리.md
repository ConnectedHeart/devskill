# 요청 중 만든 임시 파일 정리

> 분류: Java·Spring · 최근 갱신: 2026-10-27

## 한 줄 요약
요청 처리 중 원본을 가공한 사본(임시 파일)을 만들었다면 응답에 담은 직후 `finally`에서 지우되, "우리가 이번 요청에서 만든 파일인지"를 플래그로 판단하고 확장자로 판단하지 않는다.

## 내용
### 왜 문제가 되나
- 다운로드 API가 원본 문서에서 특정 요소(도장, 서명 등)를 지운 사본을 `원본파일명.tmp`로 원본 옆에 만들어 응답하고 지우지 않으면, 요청된 문서 수만큼 사본이 쌓인다. 이름이 고정이라 호출할 때마다 늘지는 않지만 문서마다 하나씩 남는다.
- 같은 문서를 동시에 두 번 요청하면 같은 경로에 동시에 쓰므로 깨진 파일이 나갈 수 있다.
- "임시파일 정리 스케줄러"가 있어도 정리 대상 폴더 목록에 그 폴더가 없으면 영원히 남는다. 스케줄러 이름만 보고 안심하지 말고 대상 폴더를 확인한다.

### 삭제 조건을 정하는 방법
- 확장자 `.tmp`로 판단하면 위험하다. 같은 API가 첨부 파일도 내준다면 사용자가 올린 `보고서.tmp` 같은 첨부는 사본 없이 원본 경로를 그대로 읽는데, 경로가 `.tmp`로 끝나 원본이 삭제된다.
- "응답 경로가 원본 경로와 다를 때"로 판단해도 동작은 맞지만 의도가 코드에 드러나지 않는다.
- 사본을 만든 분기에서 `boolean madeTempCopy = true`를 켜고 `finally`에서 그 플래그만 보고 지우는 방식이 가장 읽기 쉽고 안전하다.

### 남는 빈틈
- 사본을 쓰는 단계에서 예외가 나면 반쯤 써진 파일이 남는다. 사본 생성까지 `try` 안에 넣어야 막힌다.
- 동시 요청의 같은 파일명 문제는 파일명에 요청별 식별자(UUID, 스레드 ID)를 넣거나 `Files.createTempFile`로 만들면 사라진다.
- 이미 운영 서버에 쌓인 파일은 코드 수정으로 없어지지 않는다. 별도로 지운다.

## 핵심 코드
### 1) "이번 요청에서 만든 사본"일 때만 지우기
```java
String readPath = originalPath;
boolean madeTempCopy = false;

if (needsProcessing(originalPath)) {
    String tmp = originalPath + ".tmp";
    makeProcessedCopy(originalPath, tmp);     // 가공 사본 생성
    readPath = tmp;
    madeTempCopy = true;
}

File f = new File(readPath);
byte[] bytes;
try {
    bytes = FileUtils.readFileToByteArray(f);
} finally {
    if (madeTempCopy) {
        FileUtils.deleteQuietly(f);    // 원본 확장자가 무엇이든 원본은 절대 지우지 않음
    }
}
```

### 2) 고유 이름 사본 + 생성까지 try 안에 + 응답으로 스트리밍
```java
Path original = Paths.get(originalPath);
Path tmp = null;                                   // null이 아니면 = 이번 요청이 만든 사본
try {
    Path readPath = original;
    if (needsSanitize(original)) {
        tmp = Files.createTempFile("dl-", ".tmp"); // 요청마다 다른 이름 → 동시 요청 충돌 없음
        sanitize(original, tmp);                   // 쓰다 실패해도 finally에서 지워진다
        readPath = tmp;
    }
    response.setContentType("application/octet-stream");
    response.setContentLengthLong(Files.size(readPath));   // Servlet 3.1 이상
    Files.copy(readPath, response.getOutputStream());
} finally {
    if (tmp != null) {
        try {
            Files.deleteIfExists(tmp);
        } catch (IOException e) {
            log.warn("temp delete failed: {}", tmp, e);   // 삭제 실패를 남긴다
        }
    }
}
```

### 3) 이미 쌓인 사본 찾기 (삭제 전 목록을 사람이 확인)
```bash
# 같은 이름에서 .tmp를 뺀 원본이 옆에 있는 파일만 뽑는다(사용자가 올린 *.tmp 첨부 보호)
find <파일 루트> -type f -name '*.tmp' | while IFS= read -r f; do
  [ -f "${f%.tmp}" ] && echo "$f"
done > leftover-tmp.txt
wc -l leftover-tmp.txt
```

## 주의할 점
- `deleteQuietly`는 실패해도 예외를 내지 않는다. 삭제 실패를 알아야 한다면 반환값을 로그로 남긴다.
- 사본 경로를 원본 옆에 두면 원본 폴더 권한과 백업 범위에 들어간다. 가능하면 별도 temp 폴더를 쓴다.
