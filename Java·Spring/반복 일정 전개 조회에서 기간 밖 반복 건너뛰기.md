# 반복 일정 전개 조회에서 기간 밖 반복 건너뛰기

> 분류: Java·Spring · 최근 갱신: 2026-11-06

## 한 줄 요약
반복 일정을 "모두 읽어 와서 코드로 펼치는" 조회는 조회 기간과 상관없는 과거·미래 반복까지 펼치고 건마다 예외일을 조회해 느려진다. 조회 기간에 한 번도 들어올 수 없는 반복은 펼치기 전에 건너뛰면 결과는 같고 쿼리 수가 크게 준다. 같은 메소드 안에서 반복되는 조회는 지역 메모로 한 번만 한다.

## 내용
### 왜 느린가
- 반복 규칙(매일·매주·매월·매년, 간격, 종료 방식)을 DB에서 다 읽어 와 Java에서 날짜를 펼치는 구조가 흔하다. 반복 일정은 기간 조건으로 거르기 어려워 **기간과 무관하게 전부** 읽힌다.
- 건마다 "이 날은 제외" 목록을 따로 조회하면 N+1이 된다. 오래 쓴 사용자일수록 끝난 반복이 쌓여 느려진다.

### 건너뛰어도 되는 조건
| 종료 방식 | A: 시작일 > 조회 종료일 | B: 종료일 < 조회 시작일 |
|---|---|---|
| 종료일 지정 | 건너뜀 | 건너뜀 |
| 종료 없음 | 건너뜀 | 해당 없음 |
| N회 반복 | 건너뜀 | **적용 안 함** |

- N회 반복은 끝나는 날을 계산해 봐야 알 수 있다(예: 매주 월·수·금 10회). 그래서 B를 걸지 않는다. 이미 끝난 N회 반복은 예전처럼 펼쳐지지만 결과는 같다.
- 근거는 기존 전개 코드가 모든 유형에서 "발생일 ≥ 시작일", "(종료일 지정) 발생일 ≤ 종료일", "결과는 조회 기간 안만"을 이미 지키고 있다는 것이다. 이 세 규칙이 있으면 A·B에 걸린 반복은 결과에 한 건도 남지 않는다. 유형별로 이 세 규칙을 코드에서 하나씩 확인한다.
- 날짜 비교는 기존 전개 코드와 **같은 형식·같은 자릿수**(예: 앞 10자리 `yyyy-MM-dd`)로 한다. 호출처마다 넘기는 날짜 형식(시각 포함, UTC 변환 값)을 모두 확인한다.

### 메소드 안 반복 조회는 지역 메모
- 행마다 (종류, 소유자)별 색상 같은 설정을 조회하면 행 수만큼 쿼리가 나간다. 한 호출 안에서는 값이 바뀌지 않으므로 지역 `Map`에 담아 조합마다 한 번만 조회한다. null 결과도 기억해야 같은 조회를 반복하지 않는다.
- 메소드 지역 변수라 서버 상태가 남지 않아 다중 서버에서도 안전하다.

### 결과가 같은지와 효과 재기
- 수정 전/후 서버로 같은 요청(여러 기간: 이번 달, 과거 반복이 펼쳐지는 달, 미래 시작 반복이 있는 달, 데이터가 많은 달)을 보내 응답을 바이트 단위로 비교한다. 펼친 결과를 대량(수만 건) 대조하면 경계 실수를 잡는다.
- 시간은 수정 전/후를 **회차마다 번갈아** 잰다. 한쪽을 몰아서 재면 캐시·잡음 때문에 결과가 뒤집힐 수 있다. 첫 회는 예열로 버리고 중앙값을 쓴다.
- 쿼리 수는 DB 상태 카운터 증가분(MySQL·MariaDB `Com_select`)으로 센다. 쿼리 캐시가 꺼져 있는지 확인한다.

## 핵심 코드
### 1) 펼치기 전에 건너뛰기
```java
// 바꿔야 할 곳: 반복 정보 필드 이름, 날짜 형식(기존 전개 코드와 같은 자릿수)
String qStart = searchStart.substring(0, 10), qEnd = searchEnd.substring(0, 10);   // yyyy-MM-dd
for (EventVO ev : repeatEvents) {
    String evStart = ev.getStartDate().substring(0, 10);
    String evEnd   = ev.getEndDate() == null ? null : ev.getEndDate().substring(0, 10);
    if (evStart.compareTo(qEnd) > 0) continue;                                   // A: 아직 시작 전
    if (ev.getEndType() == EndType.UNTIL_DATE && evEnd != null
            && evEnd.compareTo(qStart) < 0) continue;                            // B: 이미 끝남(종료일 지정만)
    List<String> skipDays = eventDao.findSkipDays(ev.getEventId());              // 남은 것만 예외일 조회
    result.addAll(expand(ev, skipDays, qStart, qEnd));
}
```

### 2) 메소드 지역 메모
```java
Map<String, String> colorMemo = new HashMap<>();
for (EventVO row : rows) {
    String key = row.getType() + ":" + row.getOwnerId();
    if (!colorMemo.containsKey(key)) {                          // null 결과도 저장해 다시 조회하지 않음
        colorMemo.put(key, settingDao.findColor(row.getType(), row.getOwnerId()));
    }
    row.setColor(colorMemo.get(key));
}
```

### 3) 쿼리 수 세기 (MariaDB·MySQL)
```sql
SHOW GLOBAL STATUS LIKE 'Com_select';   -- 요청 전후 값의 차이
SHOW VARIABLES LIKE 'query_cache_type'; -- OFF 여야 정확
```

## 주의할 점
- 건너뛰기 조건을 넓히고 싶어도(N회 반복의 끝 계산 등) 전개 로직을 복제하지 않는다. 확실히 결과가 없는 경우만 거른다.
- 날짜를 문자열로 비교할 때는 두 값의 형식이 같아야 한다. 한쪽에 시각·구분자가 다르면 조용히 틀린다.
- 공용 조회 메소드면 호출처가 많다. 호출처 목록을 만들고 각 경로의 응답을 전후 비교한다.
