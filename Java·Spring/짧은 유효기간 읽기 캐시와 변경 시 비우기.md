# 짧은 유효기간 읽기 캐시와 변경 시 비우기

> 분류: Java·Spring · 최근 갱신: 2026-11-17

## 한 줄 요약
수신자마다·요청마다 같은 참조 데이터(공휴일 목록, 설정값)를 반복 조회할 때는, 호출 1회 범위의 지역 Map부터 서버 전체가 공유하는 짧은 TTL 캐시(Caffeine 등)까지 범위를 골라 쓴다. 서버 캐시는 읽기 전용·짧은 만료·변경 지점에서 비우기·끄는 스위치를 갖추면 다중 서버 환경에서도 위험이 작다.

## 내용
### 캐시 범위 고르기
| 범위 | 방법 | 공유 범위 | 맞는 경우 |
|---|---|---|---|
| 호출 1회 | 메소드 지역 `Map`을 만들어 하위 판정에 넘김 | 그 호출의 반복문 안 | 한 번의 발송에 수신자가 많을 때. 상태가 남지 않음 |
| 작업 1건 | 바깥 반복문 앞에서 Map을 만들어 매 호출에 넘김(오버로드 추가) | 그 작업 안 | 바깥이 수신자마다 하위 메소드를 따로 부를 때 |
| 서버 전체 | TTL 캐시 빈/싱글턴 | 모든 요청·경로 | 여러 경로(외부 서버가 부르는 REST 포함)가 같은 데이터를 읽을 때 |

- 호출 1회 Map은 바깥에서 하위 메소드를 수신자 1명씩 부르는 구조(대량 발송 등)에서는 효과가 없다. 그때 Map을 넘기려면 시그니처가 늘어나고, "넘기는 쪽이 판정을 책임진다" 같은 숨은 약속이 생기기 쉽다. 판정은 한 곳에만 두는 쪽이 안전하다.
- **작업 1건 범위 조회 재사용의 예(권한 판정)**: 게시글 하나를 수백 명에게 "볼 수 있는가"로 판정할 때, 판정 메서드가 사람마다 게시판 정보·게시글·직위/부서/회사 권한 행을 다시 조회하면 SQL이 후보 수 × 수십 개로 늘어난다. 이 조회들이 **넘긴 인자만으로 결과가 정해지고**(세션·서버 상태 무관) 직위·부서 ID는 많은 사람이 같으므로, 작업 하나에서 만든 조회 결과 객체를 넘겨 재사용하면 판정 규칙을 그대로 두고 SQL만 줄일 수 있다. 실측 예: 후보 510명에서 SQL 13,517개 → 4,819개, 24초 → 6.5초. 결과가 같은지는 권한 구성이 다른 여러 대상에서 수신자 목록을 수정 전후로 대조해 확인한다.
  - 기존 메서드는 그대로 두고 "조회 객체를 하나 더 받는 오버로드"를 만든 뒤, 기존 메서드는 `null`을 넘겨 새 메서드를 부르게 한다 → 다른 호출처 동작이 바뀌지 않는다.
  - 판정 코드 안의 조회 호출만 `lookupXxx(cache, 원래 인자…)`로 1:1로 바꾸면 diff에서 규칙이 그대로임이 바로 보인다.
  - key에는 그 조회의 **인자를 전부** 넣는다. 결과에 영향을 주는 플래그 하나(예: "본인 부서인가")를 빠뜨리면 다른 판정 결과가 섞인다. 인자를 이어 붙일 때는 값에 나올 수 없는 구분자(`\u0001` 등)를 써서 `"a"+"bc"`와 `"ab"+"c"`가 같은 key가 되지 않게 한다.
  - `computeIfAbsent`는 null 값을 담지 않으므로 "조회했는데 없음"도 기억하려면 `containsKey`로 확인한다.
  - Java 8 `Supplier`는 checked 예외를 던질 수 없어, `throws Exception`인 DAO를 부르려면 작은 함수형 인터페이스를 직접 만든다.
  - 사람마다 다른 값(본인 ID 권한, 개인 직급 등)은 재사용하지 않는다.
- 서버 캐시를 쓰면 시그니처를 바꾸지 않고 판정 메소드 안에서만 캐시를 쓰게 할 수 있다. 원본 조회 메소드(`getHolidays()`) 자체에 캐시를 넣지 않으면 그것을 직접 부르는 다른 화면은 영향이 없다.

### 서버 캐시 설계 조건
- **읽기 전용**: 캐시가 틀려도 결과는 "만료 시간 동안 이전 값으로 판정"뿐이어야 한다. 값은 불변 목록으로 담아 호출자가 고치지 못하게 한다.
- **짧은 만료**(예: 30초): 다중 서버에서 변경한 서버만 즉시 반영되고 다른 서버는 최대 만료 시간만큼 늦다. 이 지연을 받아들일 수 있는 데이터에만 쓴다.
- **변경 지점에서 비우기**: 저장·수정·삭제 서비스 메소드에서 evict. 인자에 키(회사 ID 등)가 없으면 전체 비우기로 통일한다. 드문 관리자 작업이면 부담이 없다.
- **끄는 스위치**: 기동 옵션(`-Dapp.holidayCacheSeconds=0`)으로 끌 수 있게 해 문제가 생기면 코드 배포 없이 되돌린다.
- 사용자마다 값이 다른 데이터(개인 설정·시간대)는 캐시하지 않는다. 한 행 조회라 효과도 작다.

## 핵심 코드
### 1) Caffeine TTL 캐시 (키: 테넌트|회사)
```java
@Component
public class HolidayCache {
    private final long ttlSeconds = Long.getLong("app.holidayCacheSeconds", 30L);
    private final Cache<String, List<Holiday>> cache = Caffeine.newBuilder()
            .expireAfterWrite(Math.max(ttlSeconds, 1), TimeUnit.SECONDS)
            .maximumSize(1000)
            .build();

    public List<Holiday> get(int tenantId, String companyId, Supplier<List<Holiday>> loader) {
        if (ttlSeconds <= 0) return loader.get();                       // 0이면 캐시 끔
        return cache.get(tenantId + "|" + companyId,
                k -> Collections.unmodifiableList(new ArrayList<>(loader.get())));
    }
    public void evictAll() { cache.invalidateAll(); }
}
```

### 2) 판정 메소드 안에서만 사용
```java
public boolean canReceive(String userId, int tenantId) {
    Prefs p = prefsDao.find(userId, tenantId);                 // 사용자별 값은 캐시 안 함
    if (!p.isSkipHolidays()) return p.isInAllowedTime(now());   // 필요 없는 사용자는 조회 자체 생략
    List<Holiday> holidays = holidayCache.get(tenantId, p.getCompanyId(),
            () -> holidayDao.findActive(p.getCompanyId(), tenantId));
    return !isHoliday(holidays, today()) && p.isInAllowedTime(now());
}
```

### 5) 작업 1건 범위 조회 재사용 객체 (빈 아님, 작업마다 new)
```java
public class LookupCache {
    public interface Loader<T> { T load() throws Exception; }   // checked 예외 허용

    private final Map<String, Object> values = new HashMap<>();

    @SuppressWarnings("unchecked")
    public <T> T get(String key, Loader<T> loader) throws Exception {
        if (values.containsKey(key)) return (T) values.get(key);  // null 결과도 재사용
        T v = loader.load();
        values.put(key, v);
        return v;
    }
}
```

### 6) 기존 API 유지 + 오버로드, 조회만 감싸기
```java
public boolean canRead(String boardId, String itemId, User u) throws Exception {
    return canRead(null, boardId, itemId, u);                      // 기존 호출처는 매번 조회
}

public boolean canRead(LookupCache cache, String boardId, String itemId, User u) throws Exception {
    for (String accessId : accessIdsOf(u)) {                       // 본인 → 직위 → 부서 → 회사
        List<Acl> acl = lookupAcl(cache, boardId, accessId, u.getTenantId());
        ... // 판정 규칙은 그대로
    }
}

private List<Acl> lookupAcl(LookupCache c, String boardId, String accessId, int tenantId) throws Exception {
    if (c == null) return aclDao.find(boardId, accessId, tenantId);
    String key = "acl\u0001" + boardId + "\u0001" + accessId + "\u0001" + tenantId;   // 인자 전부
    return c.get(key, () -> aclDao.find(boardId, accessId, tenantId));
}

// 호출하는 쪽: 알림 작업 하나마다
LookupCache cache = new LookupCache();
for (User u : candidates) if (boardService.canRead(cache, boardId, itemId, u)) recipients.add(u);
```

## 주의할 점
- 작업 범위 객체는 한 스레드에서만 쓰고 작업이 끝나면 버린다. 필드나 static에 두면 서버 메모리 캐시가 되어 다중 서버·권한 변경 반영 문제가 생긴다.
- 캐시 유무를 단위 테스트로 고정한다: "호출이 달라도 키당 1번 조회", "evict 후 다시 조회", "끄면 매번 조회", "판정이 필요 없는 사용자는 조회 0번".
- 다중 서버에서 즉시 반영이 꼭 필요한 데이터(권한 회수 등)에는 쓰지 않는다.
- 캐시 라이브러리가 이미 프로젝트에 있는지 먼저 보고, 같은 방식을 본뜬다(새 의존성 추가 최소화).
